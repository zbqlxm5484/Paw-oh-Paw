# 관절 가동 범위 (F-02)

작성 조유진 · v1 11-04 (S15P31A404-184) · 코드 `engine/joint_rom.py` · 테스트 `tests/test_joint_rom.py`

통과 하나에서 카메라 쪽 다리 6관절의 가동 범위와 각도 중앙값, 무릎의 주기별 가동 범위를 낸다. 결과 JSON v1(`docs/analysisApi/resultFormat.md`) 3절의 키와 단위 그대로 `passes[].metrics`에 들어간다. 걸음 길이·입각기 비율은 `docs/engine/gaitMetrics.md`다.

## 1. 정의

| 키 | 단위 | 정의 |
| --- | --- | --- |
| `rom_shoulder`·`rom_elbow`·`rom_carpus`·`rom_hip`·`rom_stifle`·`rom_tarsus` | `deg` | 통과에서 몸 전체가 보인 프레임 전부의 굽힘 각도 5백분위와 95백분위 사이 폭 |
| `angle_median_<관절>` | `deg` | 같은 프레임의 각도 중앙값 |
| `stifle_cycle_rom` | `{"values": [...], "unit": "deg"}` | 뒷발 주기(착지에서 다음 착지 바로 전까지)마다 무릎 가동 범위(5에서 95백분위 폭). 팀 서비스가 회차의 주기들을 모아 `stifle_cv`(표본 표준편차 ÷ 평균 × 100)를 낸다 |

- 각도는 `engine/angles.py`의 굽힘 각도(`angle_def` v1, 굽히는 쪽 면에서 잰 0에서 360°, 180° 초과는 과신전)다. 관절점 파일의 `angles`도 같은 함수(`joint_rom.frame_angles`)로 낸다
- 최솟값·최댓값 대신 5·95백분위를 쓴다. 관절점이 한두 프레임 튀어도 가동 범위가 흔들리지 않게 하려는 것이다
- 다리는 카메라 쪽만, 프레임은 **몸 전체가 화면 안에 보인 것만** 쓴다(유효 판별·보행 수치와 같음). 화면 끝에 걸린 프레임은 상자가 잘려 각도가 크게 흔들린다(4절)
- 착지 검출을 끝 프레임까지 넓히게 되더라도 가동 범위 각도는 이 규칙을 유지한다

## 2. 측정 불가

| 사유 | 언제 |
| --- | --- |
| `LOW_CONFIDENCE` | 몸이 보인 프레임 중 세 점(꼭짓점·근위·원위, 확신도 0.3 이상)을 모두 믿을 만한 프레임이 절반이 안 됨. 몸통 길이를 못 재 착지를 검출하지 못한 통과의 `stifle_cycle_rom`도 이 사유(보행 수치와 같게) |
| `NOT_ENOUGH_CYCLES` | `stifle_cycle_rom`에서 뒷발 주기가 없음 |

## 3. 가상 보행으로 확인

착지 검출 테스트의 가상 보행(60fps, 주기 0.4초)에 무릎 각도를 120 + 20 sin(주기마다 한 바퀴)로 넣었다. 사인파의 5에서 95백분위 폭은 2 × 20 × sin(81°) = 39.5다.

| 수치 | 정답 | 계산 허용 |
| --- | --- | --- |
| `rom_stifle` | 39.5 | ±2 |
| `angle_median_stifle` | 120 | ±2 |
| `stifle_cycle_rom` | 주기 5개, 각 39.5 | 각 ±3 |

점을 넣지 않은 관절은 `LOW_CONFIDENCE`(0이 아님), 짧은 통과는 가동 범위는 나오고 `stifle_cycle_rom`만 `NOT_ENOUGH_CYCLES`, 몸통 점이 없으면 `stifle_cycle_rom`이 `LOW_CONFIDENCE`인 것도 확인한다.

## 4. 어느 프레임에서 잴지: 박규원 비교 (11-04)

처음 초안은 "그 다리 발의 완전한 주기 안 프레임만" 썼다(주기 일부만 보면 덜 움직인 구간만 잡혀 작게 나올까 봐). 박규원이 이 브랜치 엔진으로 기업 영상 1,042개의 유효 통과 642개(`fs-v4` + flip 관절점)에서 네 정의를 비교했다. 재측정 차는 같은 날 촬영을 8개씩 두 묶음으로 나눴을 때 회차 값 차이의 90% 지점(개·날 중앙값)이다.

| 정의 | 쓰는 프레임 | 백분위 | 값이 나온 통과 | 재측정 차, k=8 (고관절 / 무릎 / 팔꿈치 / 어깨 / 앞발목 / 뒷발목, °) |
| --- | --- | --- | --- | --- |
| M (오차 범위 파일 근거) | 측정 구간 전부 | 10에서 90 | 96에서 97% | 4.6 / 8.0 / 8.7 / 4.6 / 11.6 / 6.2 |
| R (처음 초안) | 몸 전체가 보인 프레임 중 주기 안 | 5에서 95 | 71에서 78% | 4.5 / 5.8 / 5.8 / 4.5 / 8.8 / 5.7 (개·날 7에서 9개) |
| RC (R + 화면 끝 프레임) | 주기 안, 발끝이 안쪽이면 끝 프레임도 | 5에서 95 | 92에서 95% | 6.6 / 8.0 / 7.0 / 7.1 / 11.1 / 8.1 |
| **W (지금 정의)** | 몸 전체가 보인 프레임 전부 | 5에서 95 | **100%** | **4.7 / 5.8 / 4.8 / 5.2 / 8.8 / 7.4** (개·날 13개) |

- 주기 안만 쓰면(R) 값이 나오는 통과를 22에서 29% 잃는데 흔들림은 줄지 않는다. W는 같거나 더 작다(팔꿈치 4.8 vs 5.8). R은 값을 충분히 모은 개·날이 7에서 9개뿐이라 걸음이 고른 개만 남아 좋아 보였을 수 있다
- "주기 일부만 보면 작게 나온다"는 우려는 W에서 보이지 않았다(무릎 평균 W 51°, R 46°)
- 화면 끝 프레임을 넣으면(RC) 흔들림이 커진다(고관절 4.5 → 6.6°, 어깨 4.5 → 7.1°)
- 그래서 가동 범위·각도 중앙값은 W, 주기는 `stifle_cycle_rom`에만 쓴다
- 팀 서비스 오차 범위 파일(`config/tolerance.yaml`, MR !86)의 가동 범위 값은 M으로 낸 것이다. 정의가 W로 정해져 박규원이 같은 정의로 다시 낸다

## 5. 제니 관절점으로 측정 (11-04)

박규원이 만든 제니 관절점(30fps)의 유효 통과. 관절점 파일은 기업 데이터라 저장소에 없고 `data/tracks/`에 둔다. 재현(저장소 루트):

```
python -m engine.joint_rom data/tracks/fs-v4.track.json
python -m engine.joint_rom data/tracks/gt_videos.fs-v4-flip.track.json
```

| 관절 | 가동 범위 `fs-v4` · `flip` | 각도 중앙값 `fs-v4` · `flip` |
| --- | --- | --- |
| 어깨 | 32.4 · 31.4 | 153.8 · 155.5 |
| 팔꿈치 | 63.4 · 68.5 | 137.8 · 131.1 |
| 앞발목 | 109.3 · 105.7 | 186.7 · 182.8 |
| 고관절 | 39.1 · 45.8 | 132.9 · 131.1 |
| 무릎 | 51.5 · 59.3 | 100.9 · 102.9 |
| 뒷발목 | 48.8 · 51.9 | 117.0 · 116.7 |

- 유효 통과 26개·73개 모두 가동 범위가 나왔다(측정 불가 0건)
- 무릎 주기별 가동 범위: `fs-v4` 13주기(중앙값 51.6), `flip` 30주기(58.1). 통과당 주기가 많아야 1개라 `stifle_cv`는 회차의 여러 통과를 모아야 나온다
- 앞발목 각도 중앙값이 180°를 넘는다. 디딤 때 앞발목이 뒤로 젖혀지는(과신전) 것과 맞는다

## 6. 정확도

- 사람이 표시한 관절점으로 가동 범위 오차를 재기는 지금 정답으로 어렵다. 기업 정답은 영상에서 띄엄띄엄 뽑은 사진이라 한 통과에 몇 장뿐이다. 재려면 통과 2, 3개를 연속 프레임(통과당 30에서 60장)으로 표시해야 한다(박규원)
- 관절 각도 오차 중 한쪽으로 치우친 몫은 폭(가동 범위)을 바꾸지 않고, 프레임마다 들쭉날쭉한 몫만 폭을 넓힌다. 그래서 각도 오차(KPI-04)가 큰 앞발목·고관절도 가동 범위 오차가 그만큼 크지는 않다
