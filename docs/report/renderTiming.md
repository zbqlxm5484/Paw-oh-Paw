작성 조영운 · 2026-11-02 측정 · F-08 보고서 에픽의 REPORT 산출물

- 무엇을: 팀 서비스 워커가 촬영 1건의 결과 영상(관절점으로 골격을 그리고 사람 얼굴을 가린 MP4)을 만드는 데 걸리는 시간을 단계별로 잰다. 분석 API 시간은 뺀다(분석은 GPU 서버 몫, 명세 3절).
- 왜: 결과 영상은 팀 서버에서 가장 무거운 일이라(명세 3절 "서버 부담", 12.4 "무거운 일 나누기") 시연에서 "결과 영상 준비 중"이 얼마나 길지, 서버에서 동시 프로세스 수(`WORKER_RENDER_CONCURRENCY`)를 몇으로 둘지 정하는 근거가 된다.
- 어디에 반영: 백엔드 README 워커 절(한 줄), 199 배포 점검(팀 서버에서 같은 명령으로 재측정), 11-10 시연 준비.
- 다시 재는 법: `backend`에서 `python -m scripts.measure_render <영상.mp4>` (6절). 이 문서의 표는 그 출력이다.

## 0. 결론

- **1080p 60fps 8초 영상 1건은 이 PC에서 약 16초**(얼굴이 매 프레임 있는 최악의 경우, 서비스 기본 설정). 골격 그리기·인코딩만이면 3초, 얼굴 검출이 나머지 13초다. 지난주(10-30) 측정 20초와 같은 범위다.
- **휴대폰 기본인 1080p 30fps 8초는 약 10초**(회사 프레임 영상, 얼굴 매 프레임). 60fps의 절반이다.
- 얼굴 검출 비용은 영상 내용과 무관하게 **1080p 한 번에 약 65 ms**(4x3 타일, 1스레드), 720p는 31 ms다. 0.05초 간격 검출(150 리뷰 반영)이 매 프레임 검출보다 **2.4배 빠르고** 가려진 프레임 수는 같다.
- **이 PC(노트북)는 1~2분 넘게 돌리면 같은 일이 3배 느려진다**(검출 65 → 180~250 ms). 전원·하이브리드 코어 스케줄링 탓으로 보이며 측정값이 아니라 환경의 성질이다. 서버 값은 199 배포 점검 때 팀 서버에서 같은 명령으로 다시 잰다.
- 시연 전망: 회차 하나(촬영 16건, 1080p60)는 동시 1프로세스에서 **결과 영상이 다 나오기까지 4~5분**. 분석은 촬영마다 20~30초(명세 3절)라 결과 영상이 병목이다. 서버에서 `WORKER_RENDER_CONCURRENCY`를 올리면 그 배수로 줄고, 촬영을 30fps로 권하면 절반이다.

## 1. 무엇을 재나

워커 자식 프로세스가 `app/video/render.py`의 `render_video`로 하는 일이다(명세 7절, 12.4).

1. 원본 디코드(OpenCV)
2. 얼굴 검출: MediaPipe BlazeFace(full range) ONNX를 OpenCV DNN으로, 프레임을 480x360 타일(겹침 20%)로 나눠 타일마다 192x192 입력으로 추론. 1080p는 4x3 = 12타일. `FACE_DETECT_INTERVAL_SEC` 0.05초마다만 검출하고(60fps는 3프레임, 30fps는 2프레임마다) 사이 프레임은 마지막 상자로 가린다. 검출이 끊겨도 0.5초는 유지
3. 모자이크 + 흐림(찾은 상자가 있을 때만)
4. 골격 그리기: 관절점 파일의 22점 중 카메라 쪽 다리·귀와 몸통
5. H.264 인코딩: ffmpeg `-threads 2`, x264 veryfast, CRF 23

측정 방식 세 가지(`scripts/measure_render.py`):

| 방식 | 뜻 |
| --- | --- |
| skeleton | 1·4·5만. 얼굴 검출을 부르지 않는다(바닥값) |
| interval | 서비스 기본값. 0.05초 간격 검출 + 추적 |
| every | 매 프레임 검출(검출 비용 상한. 150 리뷰 전 동작) |

관절점은 영상 프레임 수에 맞춰 합성한 것(22점, 모든 프레임)이다. 그리는 비용은 점의 위치와 무관하다.

## 4. 해석

- **비용 구조**: 골격 그리기 + 인코딩은 1080p 프레임당 약 7 ms로 작다. 얼굴 검출이 1080p 한 번에 약 65 ms라 전체의 80% 이상이다. 60fps 8초면 160번 검출(약 10초) + 바닥 3초 + 가리기 = 약 16초.
- **간격 검출**: 60fps에서 호출 수가 1/3이라 매 프레임의 2.4배 빠르다(15.7 ↔ 37.3초). 가려진 프레임 수(480)는 같으므로 PR-C-03(얼굴 노출 0건)에 영향이 없다.
- **해상도·fps**: 720p는 타일이 6개라 검출이 절반(31 ms). 30fps는 프레임이 절반이라 전체가 절반이다. 세부명세서 최저 사양(640x360·30fps) 안에서 30fps 촬영이 가장 효과가 크다.
- **이 PC의 느려짐**: 1~2초 넘게 연속으로 돌리면 같은 검출이 65 → 180~250 ms가 된다(3.1 벤치를 두 바퀴 돌리면 둘째 바퀴부터 느리다). 영상 내용과 무관하고, 노트북의 전원 관리·P코어/E코어 배정 탓으로 본다. 워커 경로(3.4)에서는 15건 내내 16초로 일정했으니 자식 프로세스마다 새로 뜨는 구조가 이 PC에서는 오히려 유리했다. **서버 값은 서버에서 잰다**(5절).
- **시연 전망**(1080p60, 동시 1): 회차 16건 → 결과 영상 완성까지 4~5분. 분석 API가 촬영마다 20~30초이고 기관별 4건씩 보내므로 분석은 약 2분에 끝나고, 그 뒤 결과 영상이 순서대로 나온다. 결과 화면은 촬영마다 `video_status`로 "준비 중"을 보이면 된다(이미 그렇게 되어 있음, 15.6).

## 5. 권고

1. **팀 서버 `WORKER_RENDER_CONCURRENCY`**: 프로세스 하나가 약 3스레드(검출 1 + ffmpeg 2)를 쓰니 코어 수 ÷ 3 안쪽으로. 4코어면 1, 8코어면 2, 16코어면 4. 보고서 워커 1개와 API 몫을 남긴다. 199 배포 점검 때 서버에서 `python -m scripts.measure_render` 1회 돌려 이 문서 3.2 아래에 표를 더한다.
2. **촬영 안내**: 휴대폰 기본 1080p 30fps로. 60fps는 결과 영상이 두 배 걸린다.
3. **검출 간격 0.05초 유지**: 더 벌리면 빠르지만 0.5초 유지로 가리는 범위가 늘어 화면이 지저분해지고, 150 리뷰에서 0.05초를 확인했다.
4. 더 줄여야 하면 순서대로: (1) `FACE_DETECT_WIDTH`를 1280으로 내려 타일 12 → 6개(검출 절반. 멀리 있는 작은 얼굴을 놓치지 않는지 회사 프레임 20장으로 다시 확인해야 함), (2) 타일 겹침 0.2 → 0.1, (3) ffmpeg preset `ultrafast`(파일이 커진다). 모두 정확도·용량과 맞바꾸는 것이라 숫자만으로 정하지 않는다.
5. 시연 리허설(11-09)에서 회차 16건을 올려 결과 영상이 다 나오기까지 시간을 한 번 더 재서 이 문서에 적는다.

## 6. 재현 방법

`backend` 폴더에서(.env의 `FFMPEG_PATH`를 쓴다):

```
python -m scripts.measure_render <영상.mp4>                     # skeleton·interval·every 세 방식, 결과는 data/tmp/measure_render/
python -m scripts.measure_render <영상.mp4> --repeat 2 --out <폴더>
python -m scripts.measure_render <영상.mp4> --keypoints <관절점.json> --modes interval
python -m scripts.measure_render <영상.mp4> --bench-detector 20  # 검출기만 20번
```

출력이 마크다운 표라 그대로 붙인다. 시험 영상은 ffmpeg로 만들 수 있다: `ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=60 -t 8 -pix_fmt yuv420p testsrc.mp4`(얼굴 오인으로 매 프레임 가리는 최악 경우), `color=c=gray:...`(검출만).

## 7. 한계

- 측정 PC가 노트북이라 지속 성능이 일정하지 않다(4절). 절대값보다 방식 간 비율(간격 검출 2.4배, 30fps 절반)이 믿을 만하다.
- 합성 관절점이라 골격 그리기는 모든 프레임에 22점을 그린 경우다. 실제는 개가 없는 프레임은 건너뛰므로 더 짧다.
- 회사 프레임 영상은 20장을 반복한 것이라 인코딩 비용(장면 변화)은 실제 촬영과 다르다. 검출·가리기 비용은 같다.
- 분석 API 시간, 업로드·검사 시간, 보고서 PDF 시간은 포함하지 않는다. 보고서는 200(20초 측정)에서 따로 잰다.
