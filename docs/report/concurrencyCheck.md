# 백엔드 동시 처리 점검 (S15P31A404-274)

작성 조영운 · 2026-11-10~11 점검 · F-09 결과 조회·팀 서비스

- 무엇을: API와 워커를 실제로 띄우고 여러 계정이 동시에 요청을 보냈을 때 오류, 지연, 상한, 자료의 어긋남을 본다.
- 왜: 지금까지 시험은 요청을 하나씩 보냈다. 여러 요청을 실제로 동시에 보내 본 적이 없었다.
- 다시 돌리는 법: `backend`에서 API와 워커를 띄운 뒤 `python -m scripts.load_check --base-url <주소> --video <영상> [--big-video <큰 영상>] --out <결과.json>`. 시험 전용 DB에서만 돌린다(계정·반려견·회차를 만들고 지우지 않는다).
- 어디서 돌렸나: 이 PC 한 대(Windows 11, 논리 코어 22개)에서 API 1개, 워커 1개, PostgreSQL 17(Docker), 부하 스크립트가 함께 돌았다. 분석은 Mock(1건 5초)이다. nginx는 거치지 않았다. **팀 서버에서는 돌리지 않았다.**

## 0. 결론

- **자료는 어긋나지 않았다.** 두 번의 실행에서 5xx와 연결 오류는 0건이고, 겹친 촬영 순번·한 반려견의 열린 회차 둘·하루 두 줄 바이탈·멈춘 촬영·멈춘 회차·보고서가 2부가 아닌 회차가 모두 0건이다.
- **상한은 지켜졌다.** 촬영 80건이 한꺼번에 올라와도 분석 중인 촬영은 전체 16건, 기관당 4건을 넘지 않았다(0.5초마다 669번 셈).
- **문제 둘을 찾아 고쳤다.**
  1. 저장소의 빈 폴더 정리가 동시에 돌면 촬영 삭제가 500이 됐다(2절).
  2. 분석 API가 느릴 때 삭제가 몰리면 DB 연결 15개가 다 차서 다른 요청이 그동안 멈췄다(3절).
- **고치지 않은 것 셋은 정해야 한다**(4절).
  1. 보고서는 한 번에 한 부씩 만든다. 회차 4개가 함께 끝나면 마지막 회차의 보고서는 집계 48초 뒤에 나왔다(20초 기준은 첫 한두 회차만 지킨다).
  2. 결과 영상도 한 번에 하나씩 만든다. 촬영이 몰리면 결과 영상이 몇 분 뒤에 나온다.
  3. 느린 요청 40개가 한꺼번에 오면 API의 스레드가 다 찬다(시험하지 않았다. 구조에서 읽은 것이다).

## 2. 고친 것 1: 저장소의 빈 폴더 정리

- 증상: 촬영 삭제 24건을 함께 보냈을 때 1건이 500이었다(`FileNotFoundError`, `LocalStorage._prune_empty_dirs`).
- 원인: 파일을 지운 뒤 빈 폴더를 위로 올라가며 지운다. 비었는지 본 다음 지우는데, 그사이 다른 요청이 같은 폴더를 먼저 지우면 오류가 났다. 이때 촬영의 파일은 이미 지워졌고 DB는 되돌려져, 파일 없는 촬영 행이 남는다(코드로 읽은 것이다).
- 같은 뿌리의 다른 경우: 올리기가 폴더를 만든 직후(아직 비어 있다) 다른 요청의 정리가 그 폴더를 지우면 올리기가 실패한다. 스레드 8개로 재현했다.
- 고침(`app/storage/local.py`)
  - 정리는 바로 `rmdir`을 부르고 결과로 가른다. 이미 없으면 위 폴더로 넘어가고, 비어 있지 않으면 멈춘다.
  - 쓰기(`put_file`·`write_bytes`)는 폴더가 없다는 오류가 나면 폴더를 다시 만들어 다시 한다(최대 4번).
  - 지우기·세기는 그사이 없어진 파일을 0으로 센다.
  - Windows에서만: 지워지는 중인 경로는 `resolve()`가 `\\?\C:\$Extend\$Deleted\…`를 돌려주고 쓰기는 `PermissionError`를 낸다. 개발 PC에서 시험이 흔들리지 않게 이 둘을 받아 준다. 운영(Linux)의 동작은 바뀌지 않는다.
- 시험: `tests/test_storage.py`에 3개(먼저 지워진 폴더, 그사이 지워진 파일, 스레드 8개가 한 폴더 아래에서 쓰고 지우기). 고치기 전 코드에서 셋 다 실패하는 것을 확인했고, 고친 뒤 10번 돌려 모두 통과했다.

## 3. 고친 것 2: DB 연결 수

- 증상: 분석 API가 지우기 요청에 20초 걸리게 해 두고(가짜 분석 API) 촬영 삭제 24건을 함께 보냈다. 그동안 보낸 반려견 목록 조회 20건이 모두 19초 걸렸다. 삭제는 21~41초였다.
- 원인: 촬영 삭제·측정 취소·다시 분석·자료 파기는 분석 API를 부르는 동안 DB 연결을 쥐고 있다. 연결은 SQLAlchemy 기본값인 15개(5 + 10)까지였다. API는 요청을 스레드 40개에서 처리하므로, 느린 요청 15개가 연결을 다 쥐면 나머지 요청은 스레드가 남아 있어도 연결을 기다린다. 30초(SQLAlchemy 기본 `pool_timeout`)를 넘게 기다리면 500이 된다(이 경우는 코드로 읽은 것이다).
- 고침(`app/core/db.py`): 연결 수를 스레드 수와 같은 40개(평소 20 + 넘칠 때 20)로 했다. PostgreSQL 기본 `max_connections`(100) 안에서 API 두 벌(배포 전환 중)과 워커가 함께 쓸 수 있는 수다.
- 다시 재니: 같은 조건에서 목록 조회 20건이 1.0~1.4초, 삭제 24건은 모두 204(20.7~21.5초)였다.
- 남는 것: 분석 API를 부르는 동안 연결을 쥐는 것은 그대로다. 4절 3번.

## 4. 고치지 않은 것 (정해야 한다)

1. **보고서는 한 번에 한 부씩 만든다**(`app/worker/report.py`의 `REPORT_CONCURRENCY = 1`, 명세 12.4).
   - 회차가 함께 끝나면 줄을 선다. 시연 규모(4개가 함께 끝남)에서 18·28·36·48초, 과부하 규모(24개)에서 마지막이 335초였다.
   - 17.4의 "두 판본이 20초 안"(KPI-29)은 회차가 하나씩 끝날 때의 값이다. 함께 끝나면 첫 한두 회차만 지킨다.
   - 프로세스를 늘리면 줄지만 팀 서버의 코어 수(10절 Q22)를 모르고, 결과 영상과 CPU를 나눠 쓴다. 그래서 바꾸지 않았다.
2. **결과 영상도 한 번에 하나씩 만든다**(`WORKER_RENDER_CONCURRENCY` 기본 1). 촬영 118건이 몰렸을 때 시험이 끝나고 몇 분 뒤에도 43건만 만들어져 있었다. 판정과 보고서는 결과 영상을 기다리지 않는다(이번에도 그랬다).
3. **느린 요청이 스레드 40개를 다 채우면 API가 멈춘다.** 분석 API를 부르는 요청이 40개 넘게 함께 오고 분석 API가 답하지 않는 경우다. 요청 하나는 `ANALYSIS_HTTP_TIMEOUT_SEC`(30초)에서 끊기므로 그 뒤에는 풀린다. 시험하지 않았다. 줄이려면 분석 API를 부르기 전에 DB 연결을 돌려주거나 그 요청들의 동시 수를 따로 묶어야 한다.
4. **잠금을 기다리는 시간에 상한이 없다**(`lock_timeout` 없음). 이번 시험에서는 잠금 때문에 멈춘 요청이 없었다. 올리기는 회차 행을 잠근 채 영상을 임시 폴더로 옮기고 검사하는데, 2.7MB에서 0.3초, 한 회차에 8건이 함께 오면 마지막이 1.9초였다.

## 5. 보지 못한 것

- 팀 서버(EC2)에서의 값. 코어 수와 디스크가 달라 시간은 다르다.
- nginx를 거친 올리기(100MB 상한, 120초 읽기 제한).
- 실제 분석 API(GPU). Mock은 늘 5초에 끝난다.
- 워커를 껐다 켜는 중의 요청, API 두 벌이 함께 떠 있는 배포 전환 중의 요청.
- S3 저장소.
