# 실험 메모: 다시 점검할 것

2026-10-21 장준환. 아래는 실험하면서 불안했던 점입니다. GPU 서버를 받은 뒤와 추가 라벨이 들어온 뒤 다시 확인합니다.

## 공통

- [ ] 모든 영상 지표가 제니 한 마리(260820) 영상 26건 기준입니다. 다른 개에서는 결과가 달라질 수 있습니다.
- [ ] 처리 성능은 RTX 4070 노트북, Docker(WSL2) 안에서 잰 값입니다. 판정 장비(RTX 5090)에서 비율이 같게 나오는지 확인해야 합니다.
- [ ] GPU 결과는 `cudnn.benchmark` 때문에 같은 조건에서도 조금씩 흔들립니다(박규원 KPI-27 측정). 작은 차이는 노이즈일 수 있습니다.
- [ ] 정확도 KPI는 정답 205장뿐이라 3~4%p 이하 차이는 구분하기 어렵습니다(추정).

## 1. FP16 저장

- [ ] 불러올 때 FP32로 바뀌므로 속도와 메모리는 그대로입니다. 파일 크기(KPI-17)만 맞추는 방법이라, 기업이 경량화로 인정할지 물어야 합니다.
- [ ] 기업 `speed.py`가 재는 파일 크기에 FP16 파일이 그대로 잡히는지 결과로 확인합니다.

## 2. 탐지기 입력 해상도 낮추기

- [ ] 작은 탐지기(E-008~E-010)처럼 개를 놓쳐 KPI-23이 떨어질 가능성이 큽니다.
- [ ] 해상도를 바꾸면 상자 위치가 조금씩 달라지고, 관절점 모델이 보는 영역도 바뀝니다. 정확도 KPI는 정답 상자를 쓰므로 영향이 없지만, 영상 지표와 실제 서비스에는 영향이 있습니다.

## 3. 탐지 건너뛰기 + 상자 보간

- [ ] **영상 2건 시험에서 보간한 상자가 탐지기 상자와 중앙값 18px, 최대 81px 달랐고, 그 때문에 관절점도 중앙값 3.6px, 상위 10% 17px 움직였습니다.** 관절점 모델이 상자 위치에 민감합니다. 영상 지표(KPI-01, 02, 24)가 나빠지는지 반드시 봅니다.
- [ ] 보간한 프레임을 "개를 찾음"으로 세므로 KPI-23의 뜻이 조금 바뀝니다. 앞뒤 키프레임에서 모두 찾은 구간만 보간하도록 했지만, 그 사이에 개가 화면 밖으로 나갔다 들어오는 경우는 못 잡습니다.
- [ ] 기업 서비스가 실제로 이 실행 방식을 쓸지 모릅니다. 처리 성능을 우리 실행부로 재는 것은 README가 허용하지만, 납품 API에도 같은 방식이 들어가야 의미가 있습니다.
- [ ] 마지막 프레임은 항상 탐지합니다. 영상 길이에 따라 실제 탐지 횟수가 K로 나눈 값보다 조금 많습니다.

## 4. 시간 평활

- [ ] 박규원의 좌표 정규화(`ai/normalize`, F-01)와 같은 `norm` 칸을 씁니다. 둘을 합치는 순서와 담당을 정해야 합니다.
- [ ] 좌우 바로잡기(비터비) 없이 평활만 했습니다. 이름표가 뒤바뀐 프레임에서는 평활이 두 다리 사이로 점을 끌어당길 수 있습니다.
- [ ] 확신도가 낮은 점도 같이 평활합니다. 확신도 0.3 미만 점을 빼고 평활하는 방식은 아직 안 해 봤습니다.
- [ ] 착지 검출(KPI-05, 06)을 해칠 수 있는데 정답이 없어 확인하지 못합니다.
- [ ] 이 방법은 영상 지표 KPI-01, 02만 바꿉니다. 사진 한 장으로 채점하는 정확도 KPI에는 효과가 없습니다.

## 5. 미세조정 설정

- [ ] **점검에는 제니 205장 중 16장을 썼습니다. 파이프라인이 도는지만 본 것이고, 이 결과는 절대 성능으로 쓰지 않습니다.** 실제 학습에는 제니를 넣지 않습니다(개 단위 분할 규칙).
- [ ] 현행 모델은 46점을 내고 앞 22점만 씁니다. 22점 라벨 뒤에 24점을 "안 보임(0)"으로 채워 학습에서 빠지게 했습니다. 나머지 24점이 학습 중 어떻게 바뀌는지는 보지 않았습니다. RTMCC 헤드는 점들 사이 정보를 섞으므로 영향이 있을 수 있습니다.
- [ ] `--drop-untouched`로 사람이 고치지 않은 점을 빼면 205장 기준 2,907점이 빠지고 1,909점만 남습니다. 추가 라벨 3,000프레임의 `touched` 정보가 어떤지 보고 다시 정해야 합니다.
- [ ] 라벨 기준서 3-3절의 `seed` 묶음 문제(가려진 반대쪽 어깨, 고관절이 "보임"으로 표시)를 아직 처리하지 않았습니다. MMPose는 가림(1)과 보임(2)을 똑같이 학습에 씁니다. 팀과 정해야 합니다.
- [ ] 뒷다리 가중치는 `make_meta.py --hind-weight`로 바꿀 수 있게만 해 두었습니다. 지금 설정은 1.0입니다.
- [ ] 학습한 가중치를 기업 `predict.py`가 그대로 읽는지는 실제 학습 뒤에 확인합니다.
- [ ] 증강은 기본(좌우 반전, 크기와 회전)만 넣었습니다. 모션 블러, 가장자리 잘림은 albumentations 라이선스 문제로 아직 넣지 않았습니다.

## 측정 후 추가된 불안한 점 (10-21 저녁)

### 탐지 건너뛰기 처리 성능 측정이 한 번 틀렸습니다

- [ ] 처음 측정에서 K=5, 8이 현행보다 느리게(197%, 180%) 나오고 GPU 메모리가 5.5GB까지 올랐습니다. `cudnn.benchmark`가 켜져 있어 처음 보는 입력 크기마다 연산 방식을 새로 고르기 때문입니다. 영상마다 마지막 묶음의 크기가 달라서 매번 새로 골랐습니다.
- [ ] `warm()`을 다시 써서 묶음 크기 1~8을 미리 돌려 두는 방식으로 고쳐 다시 재고 있습니다. 새 결과가 나오기 전의 skip 처리 성능 숫자는 쓰지 않습니다.
- [ ] 기업 `speed.py`의 예열은 기업 실행부(탐지 8장 묶음 고정)에 맞춰져 있습니다. 실행부를 바꾸는 방식은 이런 숨은 함정이 더 있을 수 있습니다.

### 탐지기 해상도, 탐지 건너뛰기의 영상 지표

- [ ] 해상도를 낮춘 세 조건은 반려견 인식률(KPI-23)이 영상별로 최대 −8~−25%p 떨어졌고, 16~19개 영상이 하락했습니다. 개를 놓치는 일이 실제로 일어납니다. 해상도 낮추기는 이대로는 불합격입니다.
- [ ] 탐지 건너뛰기는 KPI-23이 현행과 완전히 같습니다. 다만 이것은 구조상 당연한 결과입니다(양쪽 키프레임에서 모두 찾은 구간만 보간하므로). 인식률이 지켜진다는 증거라기보다 측정 방식이 이 지표를 못 건드린다는 뜻입니다.
- [ ] 건너뛰기 K=5, 8에서 KPI-02가 크게 좋아졌지만(−18%, −32%) KPI-02의 표본 수가 150에서 156으로 바뀌었습니다. 같은 표본끼리의 비교가 아니라서 개선이라고 말할 수 없습니다. KPI-01은 K가 커질수록 오히려 나빠졌습니다(K=8에서 +9%).
- [ ] KPI-24(좌우 뒤바뀜)는 조건마다 80~96회로 흔들렸습니다. 조건 간 차이가 노이즈(±2회, 오늘 측정에서는 최대 ±8회)보다 작아 건너뛰기가 좋다 나쁘다를 말할 수 없습니다.

### 시간 평활

- [ ] **KPI-01, 02는 평활을 세게 하면 얼마든지 "좋아집니다".** 창 31프레임이면 KPI-01 −49%, KPI-02 −58%로 목표를 넘지만, 이때 발끝이 원래 위치에서 중앙값 0.5 몸통 길이나 움직입니다(보폭이 약 1 몸통 길이). 걸음 자체를 지우는 값이라 지표 개선으로 인정할 수 없습니다. 목표 −30%를 맞추려면 창 13~17 근처인데, 이 정도도 발끝이 0.16~0.24 몸통 길이 움직입니다.
- [ ] 평활이 점을 움직인 양의 상위 5%가 0.7~1.4 몸통 길이이고 최대는 17~42 몸통 길이입니다. 원래 추적 결과에 엉뚱한 곳으로 튀는 프레임(오탐, 좌우 뒤바뀜)이 있고, 평활이 그 영향을 주변 프레임으로 퍼뜨립니다. 평활 전에 튀는 값을 먼저 걷어내는 중앙값 필터와 좌우 바로잡기를 앞에 두는 방식을 시험해야 합니다(아직 안 함).
- [ ] KPI-02는 평활과 상관없이 값이 크게 흔들립니다(창 5에서 −1.5%, 창 9에서 −9%, 창 13에서 +2%). 평활의 효과가 아니라 지표의 노이즈일 가능성이 큽니다.
- [ ] 박규원의 정규화(가로 보정 끔)만 해도 KPI-01이 −8.3%였고, 평활 7을 얹으면 −21.6%였습니다. 정규화와 평활은 서로 다른 곳에서 줄여 주는 것으로 보이지만 합쳐서 −30%에는 못 미칩니다.
- [ ] 평활은 사진 한 장으로 채점하는 정확도 KPI(04, 18~22)에는 영향이 없습니다.

### 탐지 건너뛰기 재측정 결과 (10-21 16:00)

- [ ] 예열을 고친 뒤 다른 작업 없이 다시 쟀습니다. K=2, 3, 5, 8의 처리 시간 비율은 0.85, 0.79, 0.74, 0.71이고 메모리는 현행과 같았습니다. 목표 0.5에 못 미칩니다.
- [ ] **원인: 개가 화면에 있는 프레임이 영상의 약 35%뿐입니다.** 키프레임 한쪽이라도 개가 없으면 그 사이를 전부 다시 탐지하도록 만들어서, 개가 없는 구간에서는 건너뛰기가 일어나지 않았습니다.
- [ ] 다음 시험: 양쪽 키프레임 모두 개가 없으면 사이도 "없음"으로 처리. 이때 K프레임 안에 잠깐 나타난 개를 놓칠 수 있어 인식률(KPI-23)을 꼭 다시 봐야 합니다. 개가 들어오는 순간을 놓치면 통과 구간의 시작이 늦어질 수도 있습니다.
- [ ] 해상도 일괄 측정의 3회차 처리 시간이 모든 조건에서 2배 이상 튀었습니다(원인 미확인, 같은 시간대에 해설 HTML 렌더링 등 다른 작업이 있었을 수 있음). 해상도 결과도 GPU 서버에서 다시 재야 합니다.
