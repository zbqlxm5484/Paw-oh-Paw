# 1부. 기능 명세

## 1. 개요

이 문서는 크림오프 팀 서비스의 백엔드를 Python·FastAPI로 만들기 위한 기능 명세다. 팀 서비스는 SSAFY 발표에서 시연하는 서비스이면서, 기업 납품물인 결과 조회 웹(D-06)의 서버다. 측정 담당자가 반려견을 등록하고 촬영 영상을 올리면, 백엔드는 분석 API를 불러 결과를 쌓고, 회차별 재활 경과를 비교해 보여 주고, 보고서 PDF를 만든다.

- **맡는 범위**: 팀 서비스 서버(API·워커, D-06 결과 조회 웹의 서버 쪽), DB, 영상·파일 저장, 분석 API 연동, 보고서 모듈(D-07)과 견본 보고서(D-08), 결과 영상(골격 표시·얼굴 가리기)
- **맡지 않는 범위**: 분석 API와 분석 엔진(조유진), 모델 학습·경량화(장준환·허정원), 화면(장준환)
- **바뀐 점**: 역할표에는 팀 서비스를 Java·Spring으로 짓는다고 되어 있으나 Python·FastAPI로 바꾼다. 보고서 모듈과 결과 영상 처리가 이미 Python이라, 한 언어로 모으면 팀 서비스가 보고서 모듈을 함수처럼 바로 부를 수 있다. 노션 기술스택 페이지의 BACKEND 칸(Java·Spring·JPA)도 Python·FastAPI·SQLAlchemy로 함께 고친다.
- **방향**: 재활 센터 사용을 중심에 둔다. 같은 반려견을 여러 회차에 걸쳐 재고 비교하는 기능을 핵심으로 본다(5절).
- **납품 전제**: 세부명세서는 결과 조회 웹(F-09)의 달성 목표를 시연으로 두고, D-06을 프로토타입으로 받는다. 그래도 모든 납품물은 기업 운영 환경에서 동작해야 하고(PR-C-05), 실행 가이드만으로 설치할 수 있어야 한다(PR-C-06·07). 역할표는 팀 서비스를 기업 서버에 설치하지 않는다고 했지만, 화면을 D-06 겸용으로 두었고 그 화면은 이 서버 없이 돌지 않는다. 그래서 기업이 자기 서버에 설치할 수 있게 만드는 방향으로 간다(팀 합의는 10절 Q23). 저장소·분석 API·화면 주소는 설정값만 바꿔 갈아 끼울 수 있게 하고(7절, 16절), 설치 절차는 실행 가이드(D-09)에 넣는다. 실제로 설치해 쓸지와 어떤 저장소를 쓸지는 기업이 정한다(10절 Q19).
- **규모**: 지금은 서버 한 대로 시연 규모를 받는다. 전국 병원이 함께 쓰는 규모가 되어도 큰 구조를 바꾸지 않고 서버 대수를 늘릴 수 있게 맞췄다(3절 "몰릴 때와 확장 계획").

읽는 법: 기능마다 붙은 "왜"는 그 기능이 필요한 이유이고, PR·REQ·KPI·D 번호는 기업 세부명세서의 번호다. 확정되지 않은 부분은 10절 질문으로 모았다.

## 3. 전체 구조

팀 서비스 백엔드는 API 서버와 워커 두 프로세스로 나뉜다. API는 요청을 받아 바로 답하고, 분석 요청·결과 영상·보고서처럼 오래 걸리는 일은 워커가 DB에 적힌 작업 상태를 보며 처리한다.

[embedded content: 팀 서비스 백엔드 구성 · 서버 2개, 저장소 2개, 분석 대상 3개\]

강조한 분석 클라이언트가 "엔드포인트만 바꿔 쓰기"를 맡는 자리다(6절).

### 촬영 1건이 처리되는 순서

1. 담당자가 영상을 올리면 API가 검사·저장하고 촬영 행을 UPLOADED로 만든 뒤 바로 응답한다.
2. 워커가 UPLOADED 촬영을 찾아 분석 API에 보내고 작업 ID를 저장한다(SUBMITTED).
3. 워커가 2초마다 진행 중인 촬영 전체의 상태를 한 번에 조회한다(ANALYZING → DONE 또는 FAILED). 한 건이 끝나길 기다렸다가 다음 건을 보내지 않으므로, 연속으로 찍어도 뒤 촬영이 앞 촬영 때문에 밀리지 않는다(세부명세서 1.3절 "연속 촬영 시 대기 누적").
4. 완료되면 결과 JSON을 파일로 저장하고, 통과·판별 결과를 DB에 넣어 화면에 먼저 보여 준다. 결과 영상은 그다음에 따로 만들고, 준비되면 촬영에 붙인다(video\_status).
5. 화면은 2\~3초마다 촬영 목록을 다시 불러 상태를 갱신한다.
6. 담당자가 측정을 끝내면 회차 수치를 집계하고 보고서를 만든다.

처리 시간 목표는 4\~5초 영상 1건의 분석 결과까지 20\~30초다. 다만 기업은 정확도가 오르면 더 길어져도 괜찮다고 했다(10-18). 그래서 워커가 분석을 기다리는 한도는 짧게 고정하지 않고 설정값으로 둔다. 판별 결과를 결과 영상보다 먼저 보여 주면, 담당자는 영상이 그려지는 동안 다음 통과를 찍을 수 있다. 워커는 업로드·분석 완료·결과 영상 완료 시각을 남겨 처리 시간을 잰다.

### 왜 워커를 따로 두나

- 분석은 수십 초, 장비에 따라 1분 넘게 걸린다. 요청 하나를 그동안 붙잡으면 담당자는 멈춘 화면 앞에서 기다려야 한다. 워커에 넘기면 담당자는 그동안 다음 촬영을 올리거나 다른 반려견을 볼 수 있다. 병원·재활 센터에서는 필수다.
- 작업 상태가 DB에 있으므로 서버를 다시 켜도 하던 일이 이어진다. FastAPI의 BackgroundTasks는 재시작하면 작업이 사라져 쓰지 않는다.
- Redis 같은 별도 작업 큐 없이 DB를 작업 목록으로 쓴다. 구성 요소가 하나 줄고, 워커는 API와 같은 코드를 다른 명령으로 실행한다.
- **서버 부담**: 분석은 GPU 서버에서 돌고, 팀 서버는 결과를 기다리기만 한다. 팀 서버에서 무거운 일은 결과 영상 그리기와 보고서 PDF 만들기다. 워커는 이 둘을 따로 띄운 프로세스에서 정해진 개수(`WORKER_RENDER_CONCURRENCY`, 기본 1)까지만 동시에 하고, 보고서는 전용 프로세스 하나에서 따로 만든다(12.4). 워커 컨테이너에는 CPU 상한을 걸어 API 응답이 느려지지 않게 한다(16절).

### 몰릴 때와 확장 계획

영상이 한꺼번에 몰려도 서버는 멈추지 않고 줄을 세운다. 쓰는 곳이 늘면 큰 구조를 바꾸지 않고 서버 대수를 늘린다. 진짜 한계는 GPU 분석 처리량이다. GPU 서버 대수는 기업 운영이 정하고, 우리 과제는 GPU 한 장이 처리하는 양을 늘리는 것이다(KPI-14·15).

**전국 규모 가정**: 전국 동물병원 5,312곳([2025년 6월 기준](https://www.dailyvet.co.kr/?p=266449))이 하루 10마리씩(한 마리에 한 회차) 잰다고 넉넉하게 잡았다.

| 항목 | 값 | 계산 |

| 하루 촬영 | 약 85만 건 | 5,312곳 × 10회차 × 16건 |
| 하루 원본 영상 | 약 5 TB | 85만 건 × 약 6 MB |

| DB | — | PostgreSQL 한 대 | 관리형 DB(RDS)와 읽기 전용 복제본. 촬영·통과 테이블 나누기(파티션)는 그때 검토한다 |

이번 구현에서 지킬 약속은 셋이다. 파일은 `StorageService`로만 다루고, API 프로세스 메모리에 상태를 두지 않고, 상태는 조건을 건 UPDATE로만 바꾼다(11.3, 12.4). 이 셋이 지켜져야 늘릴 때 큰 구조를 바꾸지 않아도 된다.

## 4. 기능 명세

기능은 27개이며, 유저플로우의 화면 S1\~S8 순서로 묶었다. BE-22\~27은 10-30 회원가입·역할·계약 설계(팀 합의 전)다. 우선순위는 팀 시연 기준이다(필수 = 시연에 꼭 필요, 권장 = 시간이 되면).

## 5. 재활 포커스 기능

재활 센터는 같은 개를 몇 주에 걸쳐 여러 번 잰다. 그래서 "재활 시작 때와 비교해 무엇이 달라졌나"를 근거와 함께 보여 주는 것이 팀 서비스의 중심이다. 기업도 2차 멘토링에서 "조금이라도 불편한 다리를 찾는 데 도움이 되는 분석"을 가장 원한다고 했다. 다만 세부명세서가 진단성 표현과 근거 없는 변화 단정을 금지하므로(PG-05, PR-F08-03), 비교 규칙은 화면이 아니라 백엔드가 강제한다.

### 기능

- **다리 비교 요약**: 회차마다 앞다리·뒷다리의 좌우 차이를 수치별로 계산해, 차이가 큰 수치와 그 다리를 맨 위에 둔다(BE-21). 표현은 "차이가 가장 큰 다리"까지만 하고, 아프다는 판단은 하지 않는다.
- **재활 프로필**: 재활 시작일, 관심 다리(왼앞·오른앞·왼뒤·오른뒤 중 선택), 기준 회차(재활 시작 무렵 측정). 내부 메모는 담당자 화면에만 보이고 보고서에는 넣지 않는다. 진단성 문구가 섞이는 것을 막기 위해서다.
- **두 가지 비교**: 기준 회차 대비(재활 전체 경과)와 직전 회차 대비(최근 변화)를 함께 낸다.
- **추이**: 관절 가동 범위, 걸음 길이, 입각기 비율, 좌우 차이를 회차 순서대로 낸다. 관심 다리와, 다리 비교 요약에서 차이가 컸던 다리를 맨 앞에 둔다.
- **재분석 (선택)**: 분석 모델이 바뀌면 지난 회차의 원본 영상을 새 모델로 다시 분석해 같은 기준으로 비교한다. 원본 영상을 보관하는 가장 큰 이유다(7절).
- **영상 나란히 보기 (선택)**: 같은 다리의 기준 회차·최근 회차 결과 영상을 함께 재생한다.
- **경과 요약 (선택)**: 여러 회차를 한 장에 묶은 수의사용 요약이다. 10-15 회의에서 나온 "수의사가 하나만 보고 판단하기 쉽게"라는 아이디어다. 문장을 언어 모델로 만든다면 식별 정보 없는 수치만 보낸다(PR-F08-09).

### 비교 규칙

| 상황 | 백엔드가 내는 결과 | 근거 |
| --- | --- | --- |
| 보행 유형이 다름 (평보 vs 속보) | 비교하지 않는다. 같은 유형끼리만 | PR-F08-14 |
| 다리가 다름 | 같은 다리(카메라 쪽 다리)끼리만 | PR-F02-04 |
| 측정 오차 범위가 설정됨 | 범위 밖 변화만 "증가"·"감소", 안이면 "범위 안" | PR-F08-03 |
| 측정 오차 범위가 아직 없음 | 값과 차이만 내고 "변화 판단 기준 미확정" | PR-F08-03, RK-12 |
| 두 회차의 분석 모델 버전이 다름 | "분석 방식이 바뀜" 표시, 재분석하면 그 값으로 비교 | PR-F08-03, REQ-OP-006 |
| 한쪽 회차가 측정 불가 | "비교 불가 + 사유" | PR-F02-05 |

"좋아짐·나빠짐" 같은 평가 단어는 백엔드가 내지 않는다. 방향(증가·감소)만 내고, 그 뜻을 해석하는 일은 수의사에게 남긴다.

비교 응답의 항목 하나 (값은 예시, 전체 모양은 15.8):

```json
{
  "metric_code": "rom_stifle",
  "limb": "RH",
  "gait_type": "TROT",
  "unit": "deg",
  "base_value": 38.2,
  "target_value": 42.0,
  "diff": 3.8,
  "judgement": "UNKNOWN",
  "note": {"code": "RANGE_NOT_SET", "message": "변화 판단 기준이 아직 정해지지 않았습니다."}
}
```

judgement 값: INCREASE · DECREASE · WITHIN\_RANGE · UNKNOWN · NOT\_COMPARABLE

재활을 중심에 두면 역할표의 "팀 서비스가 밀리면 측정 이력·재측정 비교부터 뺀다"는 순서를 바꿔야 한다. 제안하는 빼는 순서: 영상 나란히 보기 → 경과 요약 → 재분석 → 보고서 판본을 하나로 줄이기. 이력, 비교 표, 다리 비교 요약은 끝까지 남긴다.

## 6. 분석 API 연동

팀 서비스는 분석 API를 직접 부르지 않고 "분석 클라이언트" 한 겹을 거쳐 부른다. 그래서 회사 API, 우리 개선 모델 API, 가짜(Mock) API를 설정값만 바꿔 갈아 끼운다.

처음에는 "회사에서 제공하는 API"를 부르는 구조로 생각했지만, 10-18 멘토 답변으로 바뀌었다. 기업은 모델 가중치와 원본 데이터만 주고, 분석 API는 우리가 독립적으로 만들어 넘기면 기업이 직접 연동한다. 그래서 팀 서비스가 부르는 대상은 모두 우리 분석 API(조유진)이고, 달라지는 것은 그 API가 어디서 돌고 있느냐뿐이다.

### 구조

- `AnalysisClient`는 네 동작만 정한다: `submit(영상, 촬영 정보) → job_id`, `get_status(job_id) → 상태·실패 사유`, `get_result(job_id) → 결과 JSON`, `get_keypoints(job_id) → 관절점 파일 JSON`(프레임별 22점·각도, 10-22 검토 답변 Q4).
- `HttpAnalysisClient`: 개발 환경의 우리 분석 API와, 기업 GPU 서버에 올린 같은 API를 부른다. 같은 코드라 주소만 다르다. 현행 모델과 개선 모델의 전환은 분석 API 안에서 한다(PR-F07-04).
- `MockAnalysisClient`: 견본 결과 JSON을 몇 초 뒤 돌려준다. 분석 API가 준비되기 전에 화면과 보고서를 먼저 만들 수 있고, 시연 날 분석 서버가 안 될 때의 대비도 된다.
- 설정(.env): `ANALYSIS_API_MODE=http|mock`, `ANALYSIS_API_BASE_URL`, `ANALYSIS_API_KEY`(`X-API-Key` 헤더로 보냄, 10-26 확정). 모드를 mock ↔ http로 바꿀 때는 진행 중(SUBMITTED·ANALYZING) 촬영이 없을 때 한다. DB에 남은 작업 ID가 다른 쪽 API에는 없기 때문이다.

"엔드포인트만 바꾸면 된다"는 이제 거의 그대로 맞다. 부르는 대상이 모두 우리가 만든 같은 API이기 때문이다. 남은 위험은 형식이 아니라 연결이다. 시연 때 팀 서버가 기업 GPU 서버의 API에 닿을 수 있는지(주소 공개, 방화벽, 인증)를 미리 확인해야 한다(10절 Q1).

모델은 기업 GPU 서버(H100·5080)에서 돌리되, 상시가 아니라 미리 일정을 잡아야 쓸 수 있다(10-18). SSAFY GPU 서버는 학습 전용이다. 그래서 개발 대부분은 Mock으로 하고, 실제 분석은 기업 GPU 서버 일정에 맞춰 붙여 본다. 최종 시연 날짜도 그 일정 안에 잡아야 한다.

### 결과 저장 원칙

분석 결과 JSON은 받은 그대로 파일로 보관하고, DB에는 화면과 비교에 쓰는 값만 뽑아 넣는다. 규격서 필드가 바뀌어도 원본에서 다시 뽑을 수 있고, 보고서 수치 대조(PR-F08-12)의 기준이 된다.

- 파일은 촬영 키의 `analysis.json`(7절)이다. DB에는 촬영 판정·사유·모델 이름·버전(`shot`)과 통과별 행(`walk_pass`: 순번, 카메라 쪽, 보행 유형, 유효 여부·제외 사유, 시작·끝 프레임)만 넣는다. 통과별 수치는 JSON에만 있고 회차 집계(작업 단위 8)가 거기서 읽는다.
- 분석 API의 소문자 값(판정, 보행 유형, 카메라 쪽, 사유 코드)은 `clients/analysis.py`의 대응표(`map_*`)로 우리 코드(12.2, 14.3)로 바꾸고, 바꾸는 일과 DB 쓰기는 `services/analysis_results.py`가 한다. 파일 쓰기와 조건을 건 UPDATE의 순서는 12.4를 따른다.

| 회차 집계 | 통과 묶음 → 회차 수치 (분석 쪽에서 해 주는지 확인) | S5, 보고서 |

상태 확인은 워커가 2초마다 조회한다. 분석 API가 완료 알림(콜백)을 지원하면 그 방식으로 바꿀 수 있다.

## 7. 영상 보관

원본 영상은 재분석에 필요하므로 회차가 끝나도 지우지 않고, 과제 종료 때 한꺼번에 파기한다. 화면에는 얼굴을 가린 결과 영상만 나가고, 원본은 우리 저장소(서버 디스크, 또는 팀이 쓰는 AWS S3) 밖으로 나가지 않는다.

### 무엇을 얼마나

| 파일 | 1건 크기 | 만드는 쪽 | 보는 쪽 |
| --- | --- | --- | --- |
| 원본 촬영 영상 | 약 4\~8 MB (4초 × 8\~16 Mbps) | 담당자 업로드 | 분석 API·워커만 |
| 결과 영상 (골격 + 얼굴 가림) | 인코딩 설정에 따라 다름 | 워커 | 화면 S4·S8 |
| 분석 결과 JSON | 재 봐야 함 (약 240프레임 × 22점) | 분석 API | 워커·보고서 모듈 |
| 보고서 PDF | 재 봐야 함 | 보고서 모듈 | 화면 S6, 내려받기 |

한 마리 한 회차는 16회 촬영이라 원본만 64\~128 MB다. 시연 규모를 10마리 × 3회차로 잡으면 원본은 약 2\~4 GB로, 서버 디스크 하나로 충분하다. 결과 영상까지 합쳐 회차당 약 0.25 GB로 잡으면, 반려견 50마리가 8회차씩 재도 약 100 GB다. 이전 프로젝트에서 받은 SSAFY EC2는 디스크가 약 300 GB였다. 이번 서버도 사양을 확인한다(10절 Q22). 기업 제공 데이터 전체(약 25\~32 GB)는 학습·평가 쪽에서 쓰고, 팀 서비스에는 시연에 쓸 영상만 올린다.

### 어디에 어떻게

- 저장소 접근은 `StorageService` 한 겹을 거친다. 구현은 서버 디스크(`local`)와 AWS S3(`s3`) 두 가지이고, 설정값 `STORAGE_BACKEND` 하나로 고른다. 다른 코드는 어느 쪽인지 모른다(11.11).
- 지금은 팀 EC2의 디스크(Docker 볼륨)에 둔다. SSAFY에서 받는 서버는 EC2뿐이고, 시연 규모에는 디스크로 충분하다. 기업 영상을 팀 서버에 두는 것은 과제 목적 안의 사용으로 본다. 세부명세서도 교육생 팀 장비로 개발한다고 정했다. REQ-CM-004·PR-C-02가 막는 것은 과제 밖으로 내보내는 일이고, 팀 서버는 팀만 쓰며 과제가 끝나면 파기한다. 그래서 기업에 따로 묻지 않고 진행한다(10절 Q3).
- AWS S3는 계정이 생기면 켠다(10절 Q20). EC2와 같은 판단이라 기업 허락은 따로 받지 않는다. 기업 환경에 설치하면 저장소는 기업이 고른다. 기업 서버 디스크나 서버에 연결한 NAS면 `local`(경로는 `STORAGE_ROOT`), AWS S3면 `s3`이다. S3 호환 저장소면 `s3`로 두고 그 주소를 `S3_ENDPOINT_URL`에 넣는다. 그 밖의 저장소는 `StorageService` 구현을 하나 더한다(10절 Q19). MinIO는 커뮤니티판 개발이 멈춰(2026년 GitHub 저장소가 보관 처리됨) 쓰지 않는다.
- S3는 파일을 기관·반려견·회차별로 알아서 나눠 담지 않는다. S3가 스스로 하는 일은 Intelligent-Tiering 등급으로 넣은 파일을 접근이 뜸해지면 싼 층으로 옮기는 것과, 미리 만든 수명 주기 규칙대로 옮기거나 지우는 것이다. 기관·반려견·회차별 구분은 아래 키로 우리가 한다.
- DB에는 파일이 아니라 파일 키(경로)만 저장한다. DB가 가벼워지고 파기·백업이 단순해진다.
- 키: `{기관ID}/{반려견ID}/{회차ID}/{촬영ID}/original.{mp4|mov}` · `result.mp4` · `analysis.json`, 보고서는 `{기관ID}/{반려견ID}/{회차ID}/reports/{보고서ID}.pdf`. 서버 디스크에서는 `STORAGE_ROOT` 아래 경로이고, S3에서는 버킷 안 객체 키다. 모든 ID는 UUID로 하고, 반려견 이름이나 휴대폰의 원래 파일명이 키에 들어가지 않게 한다.

압력 매트 CSV는 받지도 저장하지도 않는다. 영상만으로 분석하기로 했기 때문이다(2차 멘토링 Q16). 중간발표 때 고려했던 "압력 CSV + 영상 저장" 구조에서 바뀐 부분이다.

영상과 저장 폴더는 박규원이 정리한 데이터 보안 규칙을 똑같이 따른다. Git·메신저·개인 클라우드에 올리지 않고, 저장 폴더와 `.mp4`는 `.gitignore`에 넣는다.

### 누가 볼 수 있나

- 파일 주소는 로그인과 기관 확인을 거친 조회 API만 만들어 주고, 5분이 지나면 열리지 않는다(11.6). 서버 디스크면 우리 API가 서명을 확인하고 파일을 보낸다. S3면 S3가 서명을 확인하는 주소(presigned URL)를 주고, 버킷은 공개하지 않는다.
- 영상은 앞뒤로 넘겨 볼 수 있게 Range 요청을 지원한다. S3는 기본으로 지원한다.
- 원본 영상을 내려받는 API는 만들지 않고, 원본 키로는 S3 주소도 만들지 않는다. 분석 API에 주소로 넘기기로 하면 그 용도만 예외다(10절 Q7, 11.11).

### 결과 영상 만들기

1. 원본 영상에 프레임별 관절점으로 골격을 그린다. 관절점 파일의 프레임마다 있는 `camera_side`(`right`·`left`, 판정 못 하면 `null`)에 따라 몸통(등 가운데·엉덩이 위)과 카메라 쪽 귀·다리만 그리고 **카메라 반대쪽 귀·다리는 그리지 않는다**(세부명세서 PR-F01-04 "카메라 반대쪽 다리의 관절점은 고객 결과에 쓰지 않는다". 몸에 가려 모델이 틀리게 찍는 일이 많고, 결과 영상은 보호자·수의사가 보는 화면이다. 반대쪽 귀도 같은 이유로 뺀다, 10-29 결정). 점 집합은 `engine/camera_side.py`의 LEFT·RIGHT와 같다(왼쪽 0·3~7·14~17, 오른쪽 1·8~12·18~21). `null`이면 몸통 둘만 그린다. 판정 규칙은 분석 쪽 `engine/camera_side.py`와 같고 서버는 파일의 값을 따른다. 프레임 번호는 0부터이고 원본을 OpenCV `VideoCapture.read()`로 처음부터 차례로 읽은 순서다(분석 API도 같은 방식, 분석 API 명세에 적음).
2. 사람 얼굴을 찾아 흐리게 가린다.
3. 브라우저에서 재생되는 형식으로 저장한다. OpenCV 기본 코덱은 브라우저에서 안 열릴 수 있어 확인이 필요하다.
4. 촬영에 결과 영상 키를 연결한다.

얼굴 검출은 Google MediaPipe BlazeFace(full range) 모델을 ONNX로 바꿔 OpenCV DNN(`cv2.dnn`)으로 돌린다(모델 파일 `face_detection_full_range.onnx`, Apache-2.0, 2.1MB. `app/video/models/`에 코드와 같이 두고 출처·SHA-256·변환 명령은 그 폴더 README에 적는다. 환경 변수는 없다, S15P31A404-150). 검출은 0.05초 간격(60fps면 3프레임, 30fps면 2프레임마다)으로만 하고 사이 프레임은 마지막 상자를 유지해 가린다. 1080p 60fps 480프레임 렌더가 47초에서 20초가 되고 가려진 프레임 수는 같다(150 리뷰). 모델 입력이 192x192라 프레임을 통째로 넣으면 멀리 있는 보호자 얼굴(1080p에서 60px 안팎)이 몇 px로 줄어 놓친다. 그래서 폭 1920 이하로 줄인 프레임을 480x360쯤의 겹치는 타일(1080p면 4x3, 겹침 20%)로 나눠 타일마다 정사각형으로 채워 넣고, 점수 0.5 이상을 모아 NMS(0.3)로 합친다. 회사 프레임 20장(사람 얼굴 24개, 57~143px)에서 진짜 얼굴의 점수는 최저 0.657이라 MediaPipe 기본값 0.6은 여유가 0.06뿐이고(0.7이면 2개를 놓친다), 0.5는 24/24에 오탐 1(같은 사람의 턱 아래 상자), 0.4는 오탐 5(개 몸통 위 1)다. 개 얼굴은 잡지 않았고 1스레드 약 90~120ms/프레임이다(3x2 타일은 팔로 가린 얼굴 하나를, 2x2는 가장자리 얼굴을 놓쳤다. 프레임을 통째로 넣으면 20/24에 오탐 8). 찾은 상자를 사방 30% 넓혀 3칸 모자이크 위에 가우시안 흐림을 더해 가린다. 6칸 모자이크는 가린 결과에서 검출기가 다시 얼굴로 찾았고(모양이 남는다) 3칸은 찾지 못했다. 검출이 끊겨도 0.5초는 마지막 자리를 계속 가린다(한 프레임만 놓쳐도 얼굴이 드러난다). 골격은 가린 뒤에 그린다. 엉뚱한 곳을 가리는 쪽이 얼굴을 놓치는 쪽보다 낫다는 기준이다.

얼굴 가리기는 모델 학습·분석과 관계없다. 분석에는 원본 영상을 쓰고, 사람이 보는 결과 영상과 발표 자료에만 적용한다. 기업 영상에는 반려견을 걷게 하는 보호자·직원이 함께 찍혀 있기 때문이다. 근거는 세부명세서 REQ-CM-003(필수: 영상에 찍힌 보호자·직원의 얼굴이 결과물과 발표 자료에 노출되어서는 안 된다)과 PR-C-03(산출물의 얼굴 노출 0건)이고, 역할표에서 조영운 담당 "결과 영상의 사람 얼굴 가리기"로 배정된 일이다.

얼굴 검출 모델은 라이선스를 먼저 본다. 세부명세서 7.1은 라이브러리뿐 아니라 사전학습 가중치의 학습 데이터 조건까지 보라고 하므로("비상업 조건 데이터로 학습한 가중치는 쓸 수 없다") 둘 다 본다. Ultralytics YOLO 계열은 AGPL이라 납품물에 쓸 수 없고, 처음 골랐던 YuNet(모델 파일은 MIT)은 학습 데이터 WIDER FACE가 비상업(cc by-nc-nd) 표기라 뺐다(137 조사, 10-30). 공개 얼굴 검출기 대부분이 같은 데이터로 학습돼 있어, 모델 카드에 "구글이 동의를 받아 스마트폰으로 찍은 자체 이미지"로 학습했다고 적힌 MediaPipe BlazeFace(Apache-2.0)를 골랐다. 라이선스 원문과 변환 기록을 모델 파일 옆에 둔다. pip의 opencv-python-headless에는 Haar cascade xml이 들어 있지 않아 Haar는 후보가 아니다. 조사 전체(후보 비교, ffmpeg 코덱, 라이브러리 표)는 `docs/report/faceDetectorLicense.md`(S15P31A404-137)에 있고 D-11 반영은 QA가 한다. 팀 서비스는 기본적으로 납품 대상이 아니지만(회사에 자체 서비스가 있음) 회사가 가져갈 가능성이 있어, 애초에 7.1에 걸릴 것이 없는 모델로 정했다(10절 Q24).

### 보관과 파기

- 촬영·회차·반려견을 지우면 해당 파일도 함께 지운다.
- 과제 종료 뒤 파기 스크립트로 DB 행과 파일을 모두 지우고, 지운 파일 수·용량·시각을 기록으로 남겨 파기 확인서(D-13)에 붙인다.
- 발표 자료에는 얼굴을 가린 결과 영상만 쓰고, 질환견은 "질환견 A"처럼 적는다(REQ-CM-005).
- AWS S3를 쓰면 버킷 버전 관리를 처음부터 켜지 않는다. 한 번 켜면 끌 수 없고 일시 중지만 된다. 켜져 있으면 지워도 "지운 표시"만 생기고 예전 파일이 남아 파기가 되지 않는다. 수명 주기 규칙으로 원본을 자동으로 지우지도 않는다. 재분석에 쓰므로 과제 종료 파기 때까지 둔다.

## 8. 보고서 모듈

보고서 모듈은 팀 서비스 DB를 읽지 않는 독립 Python 패키지로 만든다. 입력 JSON을 받아 PDF를 내므로 기업 서버에도 그대로 붙고, 팀 서비스는 그것을 부르는 쪽 하나일 뿐이다(D-07 납품물).

기업이 정한 보고서 개선 순서는 사용자별 맞춤 설명 → 결과 해석 → 시각화 → 지표 구성이다(10-18). 그래서 문장(맞춤 설명·해석)을 먼저 완성하고, 차트 종류는 최소로 시작한다. 범위를 줄여야 하면 시각화부터 줄인다.

- **입력**: 회차 분석 결과(규격서 형식), 반려견 프로필(이름·체중·견종·체급), 이전 회차 결과(있으면), 판본, 설정(판정 기준, 측정 오차 범위)
- **출력**: PDF, 보고서에 실은 수치 목록(대조용), 생성 시간, 실패 사유

### 만드는 순서

1. 입력 검사: 없는 정보는 그 항목만 빼고, 만들 수 없으면 사유를 낸다 (PR-F08-02·13)
2. 수치 정리: 보행 유형별·다리별로 나누고, 측정 불가는 사유와 함께, 한 방향만 찍혔으면 "측정 조건상 비교 불가" (PR-F08-06·07·14)
3. 문장: 김지윤의 문장 템플릿으로 만든다. 외부 언어 모델은 선택이고, 쓰면 식별 정보 없는 수치만 보낸다 (PR-F08-09)
4. 차트: matplotlib. pyplot 대신 Figure 객체로 그려, 워커 프로세스에 그림이 쌓이지 않게 한다
5. HTML 템플릿 채우기: Jinja2
6. PDF 변환: WeasyPrint. 한글 글꼴은 상업 이용이 되는 OFL 글꼴(본고딕 등)을 넣는다
7. 검사: 실린 수치를 분석 결과와 자동 대조(불일치 0건), 금지 표현 목록 대조(0건), 보호자용의 설명 없는 전문 용어 검사. 하나라도 걸리면 PDF를 내보내지 않고 실패로 남긴다 (PR-F08-11·12, KPI-30·31)
8. 저장: 팀 서비스는 파일 저장소에 넣고 report 행을 갱신한다

모든 판본에 "보행 평가 보조 자료" 문구를 고정으로 넣는다. WeasyPrint는 시스템 라이브러리가 필요해 requirements.txt만으로는 설치되지 않으므로, 그 전제를 실행 가이드(D-09)에 적는다(PR-C-07).

## 9. 일정

# 2부. 구현 명세

2부는 1부를 코드로 옮길 때 지킬 정확한 약속이다. 이름, 타입, 형식을 하나로 정해 두어서, 이 부분을 GPT·Claude에 그대로 넣어도 누가 돌리든 같은 구조의 코드가 나오게 한다. 아직 정해지지 않은 값에는 10절의 질문 번호를 붙여 둔다.

### 11.3 코드 계층 규칙

- **routes**는 요청을 schemas로 검사하고 services를 부른 뒤 응답만 한다. 업무 규칙과 DB 쿼리를 넣지 않는다.
- **services**는 업무 규칙과 DB 읽기·쓰기를 맡는다. 첫 인자는 DB 세션이다.
- **models**에는 테이블 정의만 둔다.
- **report/·video/ 폴더**는 입력(dict·파일 경로)을 받아 결과를 돌려주는 함수 묶음이다. app과 DB를 모른다. 기업에 그대로 넘기기 위해서다.
- **오래 걸리는 일은 비동기 작업으로 처리한다.** 분석·결과 영상·보고서 생성은 API가 기다리지 않고 워커에 넘긴 뒤 바로 응답한다(3절). 담당자는 결과를 기다리는 동안 다음 촬영을 올리거나 다른 화면을 쓸 수 있고, 결과는 화면이 상태를 다시 조회해 받아 간다.
- **코드 문법은 `def`로 통일하고 `async def`를 쓰지 않는다.** 위의 작업 비동기와는 다른 이야기다. FastAPI는 `def`로 만든 API를 여러 스레드에서 동시에 처리하므로 한 사람의 요청이 다른 사람을 막지 않는다. 반대로 `async def` 안에서 pg8000·OpenCV·WeasyPrint처럼 일을 끝낼 때까지 멈춰 있는 라이브러리를 부르면 서버 전체가 멈춘다. AI가 만든 코드에서 자주 생기는 실수라 문법을 하나로 정해 막는다. 예외는 미들웨어(요청 ID, 요청 로그)뿐이다. Starlette 미들웨어는 async로만 쓸 수 있어 async로 쓰되, 그 안에서 DB·파일·영상 처리처럼 멈추는 일은 하지 않는다.
- SQLAlchemy는 2.0 스타일(`Mapped`, `mapped_column`, `select()`)만 쓴다. `session.query()`는 쓰지 않는다.
- Pydantic은 v2 문법(`model_config`, `field_validator`, `model_dump()`)만 쓴다.
- 모든 함수에 타입 힌트를 붙인다.
- **파일은 `StorageService`로만 다룬다.** `open()`·`os.remove()`·`shutil`로 저장소 경로를 직접 열거나 지우지 않는다. 그래야 설정값만 바꿔 서버 디스크에서 S3로 옮길 수 있다(11.11). 결과 영상·PDF를 내보내는 local 파일 API 두 곳만 예외다(11.11).
- **API 프로세스 메모리에 상태를 두지 않는다.** 로그인은 JWT로 확인하고, 요청마다 달라지는 값이나 캐시를 전역 변수에 담지 않는다. 설정·견종표처럼 바뀌지 않는 값을 읽어 두는 것은 괜찮다. 그래야 API를 여러 대로 늘릴 수 있다(3절). 예외는 담당자 스냅샷 캐시(11.6 인증 캐시) 하나다. DB 값의 60초 늦은 사본일 뿐이라 어느 프로세스에서 읽어도 같은 답이 나오고, 지워져도 다시 읽으면 된다.

### 11.4 이름·형식 규칙

| 대상 | 규칙 | 예 |
| --- | --- | --- |
| 파일·함수·변수 | snake\_case | `create_session` |
| 클래스 | PascalCase | `ShotStatus` |
| 테이블 | 단수 snake\_case | `walk_pass` |
| JSON 필드 | snake\_case | `valid_passes` |
| 상태·종류 값 | 대문자 snake\_case 문자열 | `ANALYZING` |
| ID | UUID v4. JSON은 문자열, Python은 uuid.UUID, DB에는 `UUID` | `3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90` |
| 시각 | ISO 8601 UTC, `Z`로 끝남. DB는 `TIMESTAMPTZ` UTC | `2026-10-19T00:30:00Z` |
| 날짜 | `YYYY-MM-DD` | `2026-10-19` |
| URL 경로 | `/api/v1` + 복수 명사, 소문자 | `/api/v1/dogs/{dog_id}/sessions` |

화면 표시는 한국 시간으로 바꾸는데, 이는 화면(장준환)이 맡는다.

**시각 처리**: 시각 컬럼은 `TIMESTAMPTZ`이고 모델에서는 `DateTime(timezone=True)`로 선언한다. Python에서는 `datetime.now(timezone.utc)`처럼 시간대가 붙은 시각만 쓰고, 시간대 없는 시각을 DB에 넣지 않는다. DB에서 읽은 시각은 DB 연결의 시간대로 붙어 나오므로 그 설정에 기대지 않는다. API로 내보낼 때는 `astimezone(timezone.utc)`로 바꾼 뒤 초까지만 쓰고 `Z`로 끝낸다.

### 11.5 응답 형식

- **성공**: 리소스 객체를 감싸지 않고 그대로 돌려준다. 생성은 201, 조회·수정은 200, 삭제는 204(본문 없음).
- **목록**: 페이지로 나누는 목록(반려견 목록, 측정 이력)은 `{"items": [...], "total": 45, "page": 1, "size": 20}` 모양이다. `items`는 이번 페이지에 담긴 항목 배열, `total`은 조건에 맞는 전체 개수, `page`는 지금 페이지 번호(1부터), `size`는 한 페이지에 담는 개수(기본 20, 최대 100)다. 예를 들어 반려견이 45마리면 1쪽에 20마리가 오고, 화면은 `total`을 보고 3쪽까지 있다는 것을 안다. 회차의 촬영, 보고서 판본처럼 수가 정해진 묶음은 페이지 없이 객체 안의 배열로 준다(15.1).
- **빈 값**: 값이 없는 필드도 키를 빼지 않고 `null`로 보낸다.
- **오류**: 모든 오류는 아래 한 가지 모양이다. `code`는 14절 표에 있는 값만 쓰고, `message`는 `messages/ko.yaml`에서 `code`로 찾는다. `detail`은 없으면 `null`이다.

```json
{
  "error": {
    "code": "VIDEO_PORTRAIT",
    "message": "가로로 촬영한 영상만 올릴 수 있습니다.",
    "detail": {"width": 1080, "height": 1920}
  }
}
```

- FastAPI가 기본으로 내는 입력 검사 오류(422)도 이 모양으로 바꿔 `VALIDATION_ERROR`로 낸다. 어느 필드가 틀렸는지는 `detail.fields`에 담는다.
- 예상하지 못한 오류는 500 `INTERNAL_ERROR`로만 답하고, 자세한 내용은 로그에만 남긴다. 입력 문제를 500으로 끝내지 않는다.
- 예외 하나: 허용 목록(16절 `CORS_ORIGINS`)에 없는 origin이 보낸 사전 요청(OPTIONS)은 Starlette `CORSMiddleware`가 앱에 닿기 전에 평문 `Disallowed CORS origin` 400으로 답한다. 브라우저만 보는 응답이라 위 모양을 따르지 않고, API 시험에서 결함으로 잡지 않는다.

**`detail.fields` 모양**: `{"fields": [{"field": "weight_kg", "type": "less_than_equal"}]}`. `field`는 Pydantic 오류 위치에서 첫 칸(`body`·`query`·`path`)을 빼고 나머지를 `.`로 잇는다. 요청 본문이 통째로 없으면 위치가 `body` 하나뿐이라 뺄 것이 없는데, 이때 `field`는 `"body"`다(화면은 "요청 내용이 없습니다"처럼 바꿔 보여 줄 수 있다). `type`은 Pydantic 오류 종류 그대로다. 없는 주소와 UUID 형식이 아닌 경로 ID는 404 `NOT_FOUND`다. 허용되지 않는 메서드는 HTTP 405이고, `code`는 `NOT_FOUND`로 같은 모양을 쓴다.

### 11.6 인증과 기관 분리

- **로그인**: `login_id`, `password`를 받아 JWT를 돌려준다. `institution_code`는 받지 않는다(v1.12. 아이디는 전역 유일, 12.2 `uq_staff_login`). 이후 모든 요청은 `Authorization: Bearer <token>` 헤더를 붙인다. 아이디가 없어도 가짜 해시로 bcrypt 비교를 한 번 한다(15.4). 계약이 끝난 `CLIENT`도 로그인은 된다(응답의 `effective_role`이 `GUEST`).
- **JWT 내용**: `sub`(담당자 ID), `inst`(기관 ID), `role`, `exp`. 알고리즘 HS256, 만료는 설정값(기본 12시간). 기관 ID와 역할은 토큰이 아니라 담당자 스냅샷(캐시 또는 DB)에서 가져온다. 토큰은 담당자 ID를 믿을 근거일 뿐이다.
- **역할**(저장, 12.2 `staff.role`): `ADMIN` = 크림오프 직원·사장, `/admin/*` 전부. `STAFF` = 크림오프 임시 스태프, `/admin/*` 조회만. `CLIENT` = 고객 기관 담당자. 가입으로 만들어지는 계정은 모두 `CLIENT`이고, `ADMIN`·`STAFF`는 `scripts/seed.py`로만 만든다. `ADMIN`·`STAFF`는 크림오프 자체 기관(계약 종료일 NULL)에 속한다. v1.11까지의 `STAFF`(기관 담당자)는 마이그레이션에서 `CLIENT`가 된다.
- **유효 역할** `effective_role`(계산, DB에 없다): `role`이 `CLIENT`이고 기관 계약이 `EXPIRED`면 `GUEST`, 아니면 `role` 그대로. 응답(`StaffOut`)에 들어가고 화면은 이 값으로 분기한다. `GUEST`를 저장하지 않는 이유: 역할은 사람의 권한이고 계약은 기관의 날짜다. 저장하면 날짜가 지날 때 바꾸는 작업(스케줄러)과 재계약 때 되돌리는 작업이 생기는데, 계산하면 기관의 날짜 하나로 즉시 반영된다. Spring Security가 `getAuthorities()`와 `isAccountNonExpired()`를 따로 두는 것과 같다.
- **계약 종료일** `institution.contract_ends_at`(날짜, 당일 포함, NULL은 기한 없음)과 **계약 상태** `contract_status`(계산): 종료일이 없거나 `core/dates.py`의 `today_local()`(`APP_TIMEZONE`) 이후면 `ACTIVE`, 아니면 `EXPIRED`. 연장은 날짜만 고친다.
- **계정 만들기**: 두 길이다. 디바이스 코드 가입(`POST /auth/signup`, `CLIENT`만, 15.4)과 `scripts/seed.py`(`--role ADMIN|STAFF|CLIENT`, `device_code_id`는 NULL). 비밀번호는 bcrypt 해시로만 저장한다. 관리자 계정을 만드는 API는 없다.
- **기관 분리**: 한 서버를 여러 병원·재활 센터(기관)가 함께 쓰므로, 담당자는 자기 기관의 반려견만 봐야 한다(PR-F09-04). 모든 조회·수정은 `api/deps.py`의 `get_current_staff()`가 꺼낸 기관 ID로 거른다. 예를 들어 A병원 담당자가 주소를 고치거나 잘못 받은 링크를 열어 B병원 반려견 ID로 요청하면, 404 `NOT_FOUND`로 답해 그 자료가 있는지도 알려 주지 않는다. 병원을 옮긴 반려견의 이력을 넘기는 일은 이 규칙에 예외를 두지 않고, 보호자 동의를 받는 별도 이전 기능으로 다룬다(10절 Q17).
- **영상·PDF 주소(서명 URL)**: 화면의 `<video>`·`<iframe>` 태그는 주소만으로 파일을 불러와서 로그인 토큰을 헤더에 붙이지 못한다. 그렇다고 파일 주소를 공개하면 주소를 아는 누구나 영상을 본다. 그래서 조회 API는 "이 파일 하나를 5분 동안만 열 수 있다"는 서명이 붙은 주소를 내려 준다. 예: `/api/v1/shots/{shot_id}/video?exp=1792369800&sig=9f2c...` `exp`는 만료 시각, `sig`는 서버만 아는 비밀키로 만든 값(HMAC-SHA256(비밀키, 경로 + exp))이다. 주소를 고치거나 5분이 지나면 열리지 않고, 화면은 필요할 때 조회 API를 다시 불러 새 주소를 받는다. 저장소가 S3면 이 서명 대신 S3의 presigned URL을 준다(11.11).
- **역할 검사**: `api/deps.py`의 `require_admin`(`ADMIN`만)과 `require_creamoff`(`ADMIN`·`STAFF`) 두 의존성. `/api/v1/admin/*`의 쓰기(POST·PATCH)는 앞, 조회(GET)는 뒤를 쓰고, 아니면 403 `FORBIDDEN`이다. 그 밖의 라우트는 역할을 보지 않는다(기관 필터만).
- **요청마다 하는 검사**(`get_current_staff`): ① 토큰을 풀어 담당자 ID를 얻는다(없거나 잘못됨 401 `AUTH_REQUIRED`, 만료 401 `AUTH_EXPIRED`). ② 캐시에서 스냅샷을 찾고, 없거나 지났으면 DB에서 담당자 + 기관을 읽어 캐시에 넣는다(담당자 행이 없으면 401 `AUTH_REQUIRED`). ③ `is_active`가 FALSE면 403 `ACCOUNT_DISABLED`. ④ `effective_role`이 `GUEST`면 403 `CONTRACT_EXPIRED`. `GET /auth/me`만 ④를 뺀 `CurrentStaffAny`를 쓴다. `ADMIN`·`STAFF`는 계약을 검사하지 않는다. ⑤ 경로 권한(위 역할 검사). 통과하면 스냅샷 `AuthStaff`를 돌려주고 모든 조회는 그 `institution_id`로 거른다. 토큰이 살아 있어도 ③·④에서 막히므로 로그아웃을 안 해도 다음 요청부터 차단된다(캐시 때문에 최대 60초 늦을 수 있다).
- **`/auth/me`와 로그인**: 캐시를 거치지 않고 DB를 읽고, 읽은 값으로 캐시를 갱신한다. 화면이 "새로 고침"으로 최신 상태를 볼 수 있는 자리다.
- **메일**: `core/mail.py`의 `send_mail(to, subject, body)`. 파이썬 표준 `smtplib`(STARTTLS)로 보내고 라이브러리를 더하지 않는다(D-11 행이 늘지 않는다). `SMTP_HOST`가 비어 있으면 보내지 않고 `MailUnavailable`을 낸다(API는 503 `MAIL_UNAVAILABLE`). 제목·본문은 `messages/ko.yaml`(`mail.password_reset.subject`·`.body`)에 둔다. 테스트는 가짜 발송기를 끼운다.
- **로그**: 11.8 금지 목록에 디바이스 코드, 재설정 토큰, 이메일 주소를 더한다. 가입·확인·재설정 요청의 본문과 오류 로그에 남지 않는다.

**서명 계산**: 서명할 문자열은 `{경로}` + 줄바꿈 문자 하나 + `{exp}`다. 경로는 `/api/v1`부터 쓴 전체 경로이고 쿼리는 넣지 않는다. `exp`는 Unix 초(정수)를 10진수로 쓴다. `sig`는 HMAC-SHA256 결과의 소문자 16진수(64자)다. `download`는 서명에 넣지 않고, 비교는 `hmac.compare_digest`로 한다. 함수는 `core/security.py`의 `make_signed_url(path)`과 `verify_signed_url(path, exp, sig)` 두 개다. make\_signed\_url은 주소와 만료 시각(exp)을 함께 돌려준다.

```text
키:   example-file-url-secret-000000000000
경로: /api/v1/shots/3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90/video
exp:  1792455600
sig:  71dc0ee5f533d3459657e501b062aefcaec8867af045a52eaab5b75bb3c98b95
```

위 값은 테스트에 그대로 넣어, 서명을 만드는 쪽과 확인하는 쪽이 같은 값을 내는지 확인한다.

**인증 캐시**(`app/core/auth_cache.py`): 요청마다 읽던 담당자 행을 프로세스 메모리에 `AUTH_CACHE_TTL_SEC`(기본 60초) 동안 둔다.

- **무엇을**: `AuthStaff`(frozen dataclass): `id`, `institution_id`, `login_id`, `name`, `email`, `role`, `is_active`, `institution_code`, `institution_name`, `contract_ends_at`. `effective_role`과 `contract_status`는 프로퍼티로 계산한다. ORM 객체를 넣지 않는다. 세션이 닫힌 뒤에도 쓰는 값이기 때문이다. `CurrentStaff`의 타입은 `Staff`(ORM)가 아니라 `AuthStaff`다. 라우트·서비스는 `staff.id`·`staff.institution_id`·`staff.role`만 쓰므로 호출 코드는 그대로다(`measure_session.staff_id`에 넣는 값도 같다).
- **어디에**: 프로세스 메모리의 `dict[staff_id, (만료 시각, AuthStaff)]` + `threading.Lock`. 외부 라이브러리를 더하지 않는다. 조회 때 만료된 항목은 버리고, 넣을 때 항목이 1,000개를 넘으면 만료분을 모두 치운다. 담당자 수는 기관 수 × 10 이하라 메모리는 문제가 안 된다.
- **TTL**: `AUTH_CACHE_TTL_SEC`가 0이면 캐시를 끈다(요청마다 DB). 테스트는 0으로 두고, 캐시 자체 테스트만 켠다.
- **무효화**: 같은 프로세스에서 담당자·기관을 바꾸는 API(`PATCH /admin/staff/{id}`, `PATCH /admin/institutions/{id}`, `PATCH /auth/password`, `PATCH /auth/me`, `POST /auth/password-reset/confirm`)는 바꾼 뒤 그 담당자(기관이면 그 기관의 담당자 전부)를 캐시에서 지운다. 다른 프로세스(uvicorn 워커가 여럿이거나 서버가 여럿)는 TTL이 지나야 반영된다. 워커 프로세스는 인증을 쓰지 않으므로 해당 없다.
- **대가**: 계정 중지·계약 만료·역할 변경이 최대 TTL만큼 늦게 반영된다(10절 Q28). 토큰 만료(12시간)와 `AUTH_REQUIRED`는 캐시와 상관없이 즉시다. 서버를 늘려 프로세스 사이에서 캐시를 공유해야 하면 이 모듈만 Redis로 바꾼다(3절).

### 11.7 DB 사용 규칙

- 요청 하나에 세션 하나를 쓴다(`deps.get_db`). 요청이 성공하면 `get_db`가 한 번 commit하고, 예외가 나면 rollback한다. services는 `flush()`까지만 한다.
- 워커는 바퀴(주 반복 한 번)마다 새 세션을 열고, 상태를 바꾸는 일 하나가 끝날 때마다 commit한다. 바퀴가 끝나면 세션을 닫는다.
- 테이블 변경은 Alembic 마이그레이션 파일로만 한다. DB에 직접 `ALTER`하지 않는다.
- 삭제는 실제로 지운다(행과 파일 모두). "삭제 표시"만 하는 방식은 쓰지 않는다. 과제가 끝나면 파기해야 하기 때문이다(REQ-CM-002).
- **오류가 난 뒤**: PostgreSQL은 트랜잭션 안에서 SQL 오류가 한 번 나면 rollback할 때까지 그 연결의 다음 쿼리를 모두 거부한다. DB 오류를 잡은 뒤 같은 세션으로 이어서 쓰지 않는다. 오류를 예상하고 이어 가야 하면 `db.begin_nested()`(세이브포인트) 안에서 실행한다.
- **오류 종류**: pg8000은 중복(SQLSTATE 23505)만 `IntegrityError`로 내고, 외래키(23503)·CHECK(23514) 위반은 `ProgrammingError`로 낸다. 종류를 가려야 하면 예외 클래스가 아니라 SQLSTATE로 판단한다. `app/core/db.py`의 `db_error_code(e)`가 `e.orig.args[0]["C"]`를 돌려준다.
- **격리 수준**: PostgreSQL 기본값(READ COMMITTED)을 그대로 쓴다. 상태는 조건을 건 UPDATE와 행 잠금으로 지키므로(12.4) 더 높은 수준이 필요 없다.
- **잠금 조회**: `with_for_update()`를 건 조회에는 `joinedload`를 붙이지 않는다. 외부 조인이 생기면 PostgreSQL이 "FOR UPDATE cannot be applied to the nullable side of an outer join" 오류를 낸다. 딸린 행은 잠근 뒤 따로 읽는다.

**get\_db 코드**: FastAPI 0.146은 yield 의존성의 뒷부분을 기본으로 응답을 보낸 뒤에 실행한다. 그러면 commit이 실패해도 화면은 이미 성공 응답을 받는다(시험 구현에서 확인). 그래서 `scope="function"`으로 응답 전에 commit하고, 모든 라우트는 아래 `DbSession`만 쓴다.

```python
# app/api/deps.py
SessionLocal = sessionmaker(bind=engine, expire_on_commit=False)

def get_db() -> Iterator[Session]:
    db = SessionLocal()
    try:
        yield db
        db.commit()
    except BaseException:
        db.rollback()
        delete_created_files(db)  # 12.4: 이 요청이 만든 파일을 지운다
        raise
    finally:
        db.close()

DbSession = Annotated[Session, Depends(get_db, scope="function")]
```

### 11.8 로그와 감시

- 표준 `logging`을 쓴다. 한 줄에 시각, 레벨, 요청 ID, 메시지를 남긴다. 요청 ID는 미들웨어가 만들고 응답 헤더 `X-Request-ID`로도 돌려준다.
- 로그에 남기지 않는 것: 반려견 이름, 담당자 이름, 비밀번호, 토큰, 파일 경로(PR-C-02), 디바이스 코드, 재설정 토큰, 이메일 주소(v1.12).
- (선택) `/metrics`로 요청 수·처리 시간을 Prometheus 형식으로 낸다. 수집 방식은 허정원과 정한다.

**로그로 새지 않게**: uvicorn 접근 로그는 끈다(`--no-access-log`). 쿼리 문자열에 반려견 이름(`q`)과 서명(`sig`)이 들어가기 때문이다. 대신 요청 로그 미들웨어가 메서드, 쿼리를 뺀 경로, 상태 코드, 처리 시간, 요청 ID(UUID4 16진수 32자)만 남긴다. SQLAlchemy 엔진은 `hide_parameters=True`로 만들어 오류 메시지에 값이 찍히지 않게 한다.

### 11.11 파일 저장소

파일은 `StorageService`로만 다룬다. 구현은 `LocalStorage`(서버 디스크)와 `S3Storage` 두 개이고, `get_storage()`가 `STORAGE_BACKEND`를 보고 하나를 돌려준다. 다른 코드는 어느 쪽인지 모른다.

```python
# app/storage/base.py
class StorageService(Protocol):
    def put_file(self, src: Path, key: str) -> int: ...
    def write_bytes(self, key: str, data: bytes) -> None: ...
    def read_bytes(self, key: str) -> bytes: ...
    def local_copy(self, key: str) -> AbstractContextManager[Path]: ...
    def delete(self, key: str | None) -> int: ...
    def delete_prefix(self, prefix: str) -> tuple[int, int]: ...
    def stat_prefix(self, prefix: str) -> tuple[int, int]: ...
    def file_url(self, key: str, api_path: str,
                 download_name: str | None = None) -> tuple[str, datetime]: ...
    def check_writable(self) -> None: ...

def get_storage() -> StorageService:
    """STORAGE_BACKEND에 따라 LocalStorage 또는 S3Storage를 한 번 만들어 재사용한다."""
```

| 메서드 | 하는 일 | `local` | `s3` |
| --- | --- | --- | --- |
| `put_file` | 검사를 마친 임시 파일이나 워커의 출력 파일을 키 위치에 넣고 바이트 수를 돌려준다. 같은 키가 있으면 덮어쓴다 | 같은 볼륨이면 이름만 바꾸고(`os.replace`), 다른 볼륨이면 복사한 뒤 지운다 | 올린 뒤 임시 파일을 지운다. `ContentType`은 확장자로 정한다 |
| `write_bytes`·`read_bytes` | 분석 결과 JSON처럼 작은 파일 | 임시 이름으로 쓰고 이름을 바꾼다 | 객체 하나로 쓴다 |
| `local_copy` | 결과 영상 그리기, 분석 API 제출처럼 저장된 파일을 로컬 경로로 읽어야 하는 곳 | 실제 경로를 그대로 준다 | `UPLOAD_TMP_DIR`에 내려받고, 닫을 때 지운다 |
| `delete` | 파일 하나를 지우고 바이트 수를 돌려준다. 없으면 0 | 빈 폴더도 지운다 | HeadObject로 크기를 확인한 뒤 지운다 |
| `delete_prefix`·`stat_prefix` | 접두어 아래를 지우거나 세고 (파일 수, 바이트 수)를 돌려준다. `stat_prefix`는 파기 `dry_run`에 쓴다 | 폴더를 훑는다 | 목록을 페이지마다 받는다. 1,000개씩 지우고, 응답의 `Errors`가 하나라도 있으면 예외를 내 DB 행을 지우기 전에 멈춘다 |
| `file_url` | 화면에 줄 주소와 만료 시각(`FILE_URL_TTL_SEC` 뒤) | `make_signed_url(api_path)`이 주는 주소와 exp. `download_name`이 있으면 `&download=true`를 붙인다 | presigned GET. `download_name`이 있으면 `ResponseContentDisposition`에 첨부와 파일 이름을 넣는다 |
| `check_writable` | `/health`의 저장소 검사 | 시험 파일을 쓰고 지운다 | 호출마다 다른 키로 `.health/` 아래에 쓰고 지운다 |
| `path` (`LocalStorage`만) | local 파일 API(15.2의 16·21번)가 `FileResponse`에 넘길 경로 | 실제 경로 | 없음 |

- **키**: `app/storage/keys.py`의 함수로만 만든다. 파일 키는 `original_key(inst, dog, session, shot, ext)`, `result_key(…)`, `analysis_key(…)`, `report_key(inst, dog, session, report_id)`이고, 접두어는 `institution_prefix(inst)`, `dog_prefix(inst, dog)`, `session_prefix(inst, dog, session)`, `shot_prefix(inst, dog, session, shot)`이다. 형식은 7절과 같다. 접두어는 `/`로 끝나고, `ext`는 점 없는 소문자(`mp4`·`mov`)다. `S3_PREFIX`는 `S3Storage`가 앞에 붙이며 DB에 저장하는 키에는 넣지 않는다.
- **주소**: `*_url`의 값은 `file_url`만 만든다. `local`이면 `/api/v1`부터 쓴 상대 주소, `s3`면 절대 주소다(15.1). `s3`일 때 파일 API(15.2의 16·21번)는 쓰이지 않고, 불리면 404 `NOT_FOUND`다. local의 16·21번은 `LocalStorage.path(key)`로 경로를 얻어 `FileResponse`로 보낸다(11.3의 예외).
- **내려받는 이름**: `app/services/reports.py`의 `report_download_name(dog, session, edition)` 하나로 만들고, local의 21번과 s3의 presigned URL이 함께 쓴다. `Content-Disposition`에는 ASCII 대체 이름(`report.pdf`)과 `filename*=UTF-8''<퍼센트 인코딩>`을 함께 넣는다(15.7).
- **원본 영상**: 원본 키로는 `file_url`을 부르지 않는다(BE-12). 분석 API에 주소로 넘기기로 하면(10절 Q7) 그때 별도 메서드를 정한다.
- **AWS S3 버킷**: 공개 차단(Block Public Access)을 켜고, 버전 관리는 처음부터 켜지 않는다(7절). 리전 기본값은 서울(`ap-northeast-2`)이다. 자격 증명은 EC2에 붙인 IAM 역할을 쓰고, 역할을 쓸 수 없을 때만 `S3_ACCESS_KEY_ID`·`S3_SECRET_ACCESS_KEY`를 넣는다. 권한은 그 버킷의 GetObject·PutObject·DeleteObject·ListBucket만 준다.
- **S3 연결**: boto3 클라이언트에 연결·읽기 제한 시간(각 3초)과 재시도 2회를 건다. `/health`는 저장소 검사에서 난 모든 예외를 잡아 `"storage": "error"`와 503으로 답한다.
- **시험**: 같은 테스트를 `LocalStorage`와 `S3Storage`에 모두 돌린다. S3는 moto로 흉내 낸다.

### 12.3 회차 수치 코드

`session_metric.metric_code`에 들어가는 값이다. 세부명세서 6.2.1절의 회차 단위 수치를 옮겼다. 거리 수치는 화면상 몸통 길이로 나눈 상대값이고 cm가 아니다.

| metric\_code | 수치 | 단위(unit) | limb |
| --- | --- | --- | --- |
| `rom_shoulder` | 어깨 관절 가동 범위(5\~95 백분위 폭) | `deg` | LF, RF |
| `rom_elbow` | 팔꿈치 가동 범위 | `deg` | LF, RF |
| `rom_carpus` | 앞발목 가동 범위 | `deg` | LF, RF |
| `rom_hip` | 고관절 가동 범위 | `deg` | LH, RH |
| `rom_stifle` | 무릎 가동 범위 | `deg` | LH, RH |
| `rom_tarsus` | 뒷발목 가동 범위 | `deg` | LH, RH |
| `angle_median_<관절>` | 위 6개 관절 각도의 중앙값. 예: `angle_median_stifle` | `deg` | 관절에 맞는 다리 |
| `stifle_cv` | 무릎 움직임 일관성(보행 주기 사이 변동계수) | `pct` | LH, RH |
| `paw_lift` | 발 높이(최대 들림) | `pct_body` | LF, RF, LH, RH |
| `paw_excursion` | 발 움직임 범위(앞뒤 이동 폭) | `pct_body` | LF, RF, LH, RH |
| `stride_length` | 걸음 길이 | `pct_body` | LF, RF, LH, RH |
| `stance_ratio` | 입각기 비율 | `pct` | LF, RF, LH, RH |
| `walk_speed` | 보행 속도 | `body_per_sec` | NONE |
| `gait_cycles` | 측정된 보행 주기 수 | `count` | NONE |

- 단위 코드: `deg`(°), `pct`(%), `pct_body`(몸통 길이 대비 %), `body_per_sec`(몸통 길이/초), `count`(회).
- 좌우 차이와 대칭 지수는 저장하지 않고, 같은 회차·보행 유형의 왼쪽·오른쪽 값으로 계산한다. 좌우 차이 = 왼쪽 − 오른쪽(원 단위), 대칭 지수 = |왼쪽 − 오른쪽| ÷ ((왼쪽 + 오른쪽) ÷ 2) × 100(%). 한쪽이 측정 불가면 "비교 불가"다. 세부명세서에 대칭 지수 식이 없어 널리 쓰는 식을 넣었고, 분석 엔진이 다른 식을 쓰면 그쪽을 따른다(10절 Q6).
- 코드 이름은 분석 결과 JSON 형식이 정해지면(10절 Q2·Q6) 그 이름에 맞춘다. 그 전까지는 이 이름을 쓴다.

| `shot.status` | UPLOADED → SUBMITTED → ANALYZING → DONE (SUBMITTED → DONE도 가능). UPLOADED·SUBMITTED·ANALYZING → FAILED. FAILED → UPLOADED(다시 분석) | 업로드·다시 분석은 API, 나머지는 워커 | 분석 중 시간 초과는 설정값(기본 600초). 정확도가 우선이라 넉넉하게 둔다. 다시 분석하면 `fail_reason`을 비우고 `attempt_count`를 0으로 돌린다 |
| `shot.video_status` | PENDING → READY 또는 FAILED | 워커 | `status`가 DONE이 된 뒤에 시작한다. 결과 영상이 실패해도 판정 결과는 그대로 쓴다 |
| `measure_session.status` | MEASURING → AGGREGATING → DONE 또는 FAILED | 측정 종료 API → 워커 | 측정 종료를 누르면 바로 AGGREGATING이 되고 업로드가 막힌다. 워커는 그 회차의 촬영이 모두 DONE 또는 FAILED가 된 뒤에 집계를 시작한다. 담당자는 마지막 촬영의 분석을 기다리지 않고 종료해도 된다 |
| `report.status` | PENDING → GENERATING → DONE 또는 FAILED. 워커가 켜질 때 GENERATING → PENDING | 워커, 다시 만들기 API(→ PENDING) | 워커는 회차를 DONE으로 바꾸는 같은 트랜잭션에서 판본마다 1행을 PENDING으로 만든다. 화면이 DONE인데 보고서 행이 없는 순간을 보지 않게 하기 위해서다 |

- 상태는 조건을 건 UPDATE로만 바꾼다. 예: `UPDATE shot SET status='SUBMITTED' WHERE id=:id AND status='UPLOADED'`. 바뀐 행이 0개면 다른 처리가 먼저 가져간 것이므로 건너뛴다. 같은 일을 두 번 하지 않기 위해서다.
- 분석 API 제출이 네트워크 오류로 실패하면 `attempt_count`를 올리고 다음 차례에 다시 보낸다. 그동안 촬영은 SUBMITTED에 머물고 `job_id`는 비어 있다(화면에는 대기로 보인다). 3번 실패하면 FAILED(`ANALYSIS_SUBMIT_FAILED`)다. 분석 API가 요청 자체를 거부하면(400·413·415처럼 다시 보내도 같은 4xx) 다시 보내지 않고 바로 FAILED(`ANALYSIS_SUBMIT_FAILED`)다(87 MR 리뷰). 다시 보내는 것은 연결 실패·시간 초과·5xx·깨진 응답·408·429다. 401·403은 요청이 아니라 인증 키(`ANALYSIS_API_KEY`) 설정 문제라 촬영을 건드리지 않는다: `attempt_count`를 올리지 않고 로그만 남긴 뒤 그 바퀴의 제출(과 상태 조회)을 멈추고, 키를 고치면 다음 바퀴에 그대로 이어 보낸다. 못 고치면 `ANALYSIS_TIMEOUT_SEC` 뒤 시간 초과로 끝난다. 키 하나가 틀렸다고 대기 중인 촬영이 전부 FAILED가 되지 않게 하기 위해서다(MR !34 검토).
- 상태·결과 조회에서 분석 API가 작업이 없다고 답하면(404·410. 재시작으로 작업을 잃었거나 보관 기간이 지남) 기다려도 오지 않으므로 바로 FAILED(`ANALYSIS_FAILED`)다. 409(아직 결과 없음)·5xx·연결 실패는 다음 바퀴에 다시 묻고 시간 초과가 끝을 낸다. 결과를 DB에 넣다가 오류가 나면 방금 쓴 파일을 지우고 그 촬영만 건너뛴다(다음 바퀴에 다시). 한 촬영의 오류가 같은 바퀴의 다른 촬영·가져오기·제출을 막지 않는다. 결과 JSON의 값은 DB 범위(`pass_no` SMALLINT, 프레임 INTEGER)까지 미리 검사해 저장 중 형식 오류가 나지 않게 한다.
- 워커는 파일(분석 결과 JSON, 결과 영상, 보고서 PDF)을 먼저 쓰고, 그 키를 조건을 건 UPDATE로 행에 붙인다. 바뀐 행이 0개면(그사이 담당자가 촬영·회차를 지웠거나 파기했으면) 방금 쓴 파일을 지운다. DB에 키가 없는 파일이 남으면 파기에서 빠지기 때문이다(REQ-CM-002).

* **잠금**: 워커는 하나만 띄운다(docker-compose의 `worker` 1개). API에서 상태를 확인하고 바꾸는 동작(업로드, 측정 종료, 측정 취소, 촬영 삭제, 다시 분석)은 그 회차 행을 `SELECT … FOR UPDATE`로 잠근 뒤 확인한다. 회차 시작은 반려견 행을 잠근 뒤 MEASURING 회차가 있는지 본다. 워커도 회차를 집계하거나 DONE으로 바꿀 때 같은 회차 행을 잠근다. 워커가 UPLOADED 촬영을 가져갈 때도 같다: 그 회차 행을 잠근 뒤 조건을 건 UPDATE로 SUBMITTED로 바꾸고 commit한 다음에 분석 API를 부른다. 그래서 측정 취소·촬영 삭제는 UPLOADED를 막지 않아도 된다. 취소가 먼저 잠그면 워커는 이미 지워진 행을 보고 건너뛰고(바뀐 행 0개), 워커가 먼저 잠그면 취소는 SUBMITTED를 보고 409 `SHOT_IN_PROGRESS`를 낸다.
* **API가 만든 파일**: 업로드처럼 요청 안에서 파일을 만들면 그 키를 `db.info["created_files"]`에 넣는다. commit이 실패하면 `get_db`가 그 파일을 지운다(11.7). 지울 때는 12.5 순서대로 파일을 먼저 지운다. 행 삭제가 실패해 파일 없는 행이 남는 것은 괜찮다(파기 때 함께 지워진다). 반대로 DB에 키가 없는 파일이 남으면 파기에서 빠진다.
* **보고서 행 값**: `template_version`에는 보고서 모듈의 `report.TEMPLATE_VERSION` 상수를 넣는다.
* **무거운 일 나누기**: 워커의 주 반복(2초마다)은 분석 제출·상태 조회·결과 저장·회차 집계처럼 가벼운 일만 한다. 결과 영상과 보고서 PDF는 `app/worker/render.py`가 프로세스 풀 두 개에 맡기고, 끝나기를 기다리지 않는다. 결과 영상 풀은 `WORKER_RENDER_CONCURRENCY`개, 보고서 풀은 1개다. 보고서가 결과 영상 뒤에서 기다리지 않게 하기 위해서다(BE-15). 두 풀 모두 `ProcessPoolExecutor(mp_context=multiprocessing.get_context("spawn"))`로 만든다. fork로 만들면 DB 연결 풀이 자식 프로세스에 복사된다.
* **자식 프로세스**: `video/`·`report/` 함수만 부르고 DB와 저장소를 모른다(11.3). 주 반복이 작업마다 `UPLOAD_TMP_DIR/worker/{작업 ID}/` 폴더를 만들고, 입력 경로와 출력 경로를 넘긴다. 입력은 `local_copy`로 준비하고, 작업별 `ExitStack`으로 작업이 끝날 때까지 열어 둔다. 자식 프로세스는 OpenCV 스레드를 1개(`cv2.setNumThreads(1)`)로, ffmpeg를 `-threads 2`로 묶는다.
* **맡기기와 거두기**: 빈 자리는 그 풀에서 실행 중인 작업 수가 풀 크기보다 적을 때다. 미리 줄 세워 넣지 않는다. 결과 영상은 `status='DONE' AND video_status='PENDING'`인 촬영을 `analyzed_at, id` 순으로, 보고서는 PENDING 행을 `updated_at, id` 순으로 꺼낸다. 맡긴 ID는 메모리 집합에 두어 두 번 맡기지 않는다. 주 반복은 매 바퀴 `future.done()`으로 끝난 작업을 거둔다. `add_done_callback` 안에서는 DB를 건드리지 않는다. 성공이면 출력 파일을 `put_file`로 넣고 조건을 건 UPDATE로 붙인다. 성공·실패 모두 `ExitStack`을 닫고 작업 폴더를 지운다.
* **보고서 한 건**: 주 반복이 `UPDATE report SET status='GENERATING' WHERE id=:id AND status='PENDING'`으로 가져가 commit한 뒤 맡긴다. 입력 dict는 `app/services/report_input.py`의 `build_report_input(db, report)`가 만든다(8절의 입력). 끝나면 `status='DONE'`, `file_key`, `generation_ms`(자식 프로세스가 PDF를 만든 시간), `model_version`, `template_version`, `fail_reason=NULL`을 `WHERE id=:id AND status='GENERATING'`으로 쓴다. 보고서 모듈은 검사 실패를 `report.ReportCheckError`로 알리고 이는 `REPORT_CHECK_FAILED`, 그 밖의 예외는 `REPORT_FAILED`다. 보고서 키는 보고서 ID로 정해져 다시 만들어도 같다. 그래서 새 PDF로 덮어쓰고, 예전 파일을 따로 지우지 않는다.
* **자식 프로세스가 죽으면**: `BrokenProcessPool`이 나면 그 풀을 새로 만들고, 그 풀에서 실행 중이던 작업을 모두 FAILED(`VIDEO_RENDER_FAILED`·`REPORT_FAILED`)로 둔다.
* **다시 켤 때**: 워커가 켜지면 `UPLOAD_TMP_DIR/worker/`를 비우고, GENERATING 보고서를 PENDING으로 돌린다. 만들던 중에 꺼진 것이기 때문이다. 결과 영상은 PENDING에 머물러 있으므로 그대로 다시 맡긴다. 이 규칙은 워커가 한 대일 때만 맞다(3절 확장 계획).
* **기관별 상한**: UPLOADED 촬영을 고를 때 `shot → measure_session → dog`를 join해 기관별 SUBMITTED·ANALYZING 수를 GROUP BY로 센다. 후보 조회는 기관별로 올린 순서에 번호를 매겨(`row_number() OVER (PARTITION BY 기관 ORDER BY uploaded_at, id)`) 그 기관의 남은 자리(`WORKER_MAX_IN_FLIGHT_PER_INSTITUTION` − 진행 중) 이하인 것만 남기고, 전체는 올린 순서로 남은 전체 자리(`WORKER_MAX_IN_FLIGHT` − 진행 중)만큼만 읽는다(LIMIT). 그래서 한 기관이 앞에 많이 올려도 그 뒤 다른 기관의 촬영이 보이고, 대기열이 아무리 길어도 바퀴마다 읽는 행은 남은 자리 수다. 한 바퀴 안에서 가져올 때마다 메모리의 개수도 늘리는데 이것은 안전망이다. 한 기관이 한꺼번에 많이 올려도 전체 자리를 다 차지하지 못하고, 다른 기관의 새 촬영은 전체 자리가 남아 있으면 바로 가져간다(3절).

### 12.5 데이터 규칙

- **이름**: 회차 테이블은 `measure_session`, 모델 클래스는 `MeasureSession`이다. SQLAlchemy의 DB 세션(`Session`)과 이름이 겹치면 AI가 둘을 헷갈린 코드를 만들기 때문이다. API 주소와 JSON에서는 그대로 `sessions`, `session_id`를 쓴다.
- **삭제 순서**: DB의 연쇄 삭제(ON DELETE CASCADE)를 쓰지 않는다. 행을 지울 때 파일도 같이 지워야 하는데 DB는 파일을 모르기 때문이다. 서비스가 이 순서로 지운다: 파일 → `walk_pass` → `shot` → `session_metric` → `report` → `dog.baseline_session_id`를 NULL로 → `measure_session` → `dog`. 기관을 지우는 기능은 없으므로 `device_code`는 지우지 않고 회수(`revoked_at`)만 한다.
- **측정 불가**: `value`는 NULL, `measurable`은 FALSE, 사유는 `unmeasurable_reason`에 넣는다. 0을 넣지 않는다. 0은 측정값으로 오해되기 때문이다(PR-F02-05).
- **체급 분류**: 체급은 등록 체중만으로 나눈다(박규원의 체급 기준 자료, 10-22. v1.3까지는 견종 기준이었다). 세부명세서가 체급을 쓰는 곳은 소형견이 화면에 작게 찍히는 문제(RK-09), 체급별 권장 통과 수(D-14), 보고서 맞춤 설명(PR-F08-02)인데, 분석 쪽의 체급별 KPI 집계(KPI-08·25·26)와 개 보행 임상 연구(압력 매트)가 같은 체중 경계를 쓴다. 백엔드가 견종으로 나누면 분석 쪽 집계와 보고서의 체급이 어긋나므로 같은 규칙을 쓴다. 규칙은 다음과 같다.
  1. 등록 체중이 10 kg 미만이면 SMALL, 25 kg 미만이면 MEDIUM, 25 kg 이상이면 LARGE다. 경계값은 설정값(16절)이고, 경계에 있는 값은 위 구간에 든다(10.00 kg은 MEDIUM, 25.00 kg은 LARGE).
  2. `config/breeds.yaml`은 화면의 견종 자동완성용 이름 목록이다. 화면에서는 견종을 이 목록에서 고르고, 없으면 직접 입력한다. 체급 분류에는 쓰지 않는다.
  3. 담당자가 체급을 고치면 `size_class_manual`을 TRUE로 하고, 이후 자동으로 바꾸지 않는다. `size_class`에 `null`을 보내면 FALSE로 돌아가 저장된 체중으로 다시 정한다.
  4. 체중을 고치면 `size_class_manual`이 FALSE일 때만 새 체중으로 다시 정한다. 견종을 고쳐도 체급은 바뀌지 않는다.
  5. 이 규칙은 박규원의 체급별 권장 통과 수 분석(D-14)·KPI 집계와 같은 것이다. 분류는 `classify_size(weight_kg)` 함수 하나로 두고 양쪽이 함께 쓴다(10절 Q15).
  6. 회차에는 시작 시점의 체급을 따로 저장한다(`measure_session.size_class`, 팀 회의 10-22). 담당자가 반려견 체급을 직접 지정했으면 그 값, 아니면 그날 체중(`weight_kg`, 없으면 등록 체중)으로 계산한다. 그 뒤 반려견 체중·체급이 바뀌어도 지난 회차의 체급은 그대로이고, 집계·보고서는 회차의 체급을 쓴다. 대형견도 새끼일 때는 소형 구간에 들고, 감량한 개는 그 뒤 회차부터 중형이 된다. 측정 수치는 체급과 상관없이 그대로이고 체급별 기준 문장만 회차의 체급을 따른다.
- **기준 회차**: `baseline_session_id`가 비어 있으면 그 반려견의 가장 이른 DONE 회차를 기준으로 쓴다. 회차 순서는 언제나 (measured\_on, created\_at) 오름차순이고, 가장 이른·가장 최근·바로 앞 회차를 모두 이 순서로 정한다. 측정일을 직접 고를 수 있고 같은 날 회차가 둘일 수 있어서다.
- **촬영 순번**: `seq_no`는 같은 회차의 가장 큰 값 + 1이다. 동시에 올려도 겹치지 않도록 업로드는 회차 행을 SELECT … FOR UPDATE로 잠근 뒤 순번을 매긴다(12.4). 그런데도 겹치면(`uq_shot_seq` 위반) 잠금이 빠진 버그이므로 500으로 끝내고 로그를 남긴다.
- **활성 계정 수**(v1.12): 디바이스 코드 하나로 가입했고 `is_active`가 TRUE인 계정 수다. `SELECT count(*) FROM staff WHERE device_code_id = :id AND is_active`. 가입은 `device_code` 행을 `SELECT … FOR UPDATE`로 잠근 뒤 세고 넣는다. 동시에 가입해도 상한(`max_accounts`)을 넘지 않게 하기 위해서다(촬영 순번과 같은 방식). 퇴사자를 중지하면 자리가 돌아온다.
- **반려견 `version`**(v1.12): 수정할 때마다 1 늘고, 수정 요청은 읽었을 때의 `version`을 보내야 한다. SQLAlchemy `version_id_col`로 ORM이 `WHERE version = :old`를 붙이고, 어긋나면 `StaleDataError`를 409 `DOG_MODIFIED`로 바꾼다. JPA `@Version`과 같다. 회차·촬영은 이미 행 잠금으로 지키므로(12.4) 자유 수정이 있는 행은 반려견뿐이다.
- **재설정 토큰**(v1.12): 계정당 하나다. 새로 요청하면 이전 토큰은 덮어써서 무효가 된다. 서버가 `secrets.token_urlsafe(32)`로 만들어 메일로 보내고, DB에는 SHA-256 해시와 만료 시각(발급 30분 뒤)만 둔다. 쓰면 지운다.
- **도구**: PostgreSQL 17, SQLAlchemy 2(테이블을 Python 클래스로 정의), pg8000(Python에서 PostgreSQL에 접속하는 드라이버), Alembic(테이블 변경 이력을 파일로 남겨 팀원 누구나 같은 DB를 만든다. Spring의 Flyway와 같은 역할).
- **상태·종류 값**: PostgreSQL의 ENUM 타입을 쓰지 않고 `VARCHAR(20)` + CHECK 제약으로 둔다. ENUM 타입은 값을 빼거나 이름을 바꾸기 어렵고 Alembic 마이그레이션도 번거롭다. 모델에서는 `String(20)` 컬럼에 `__table_args__`의 `CheckConstraint`로 DDL과 같은 이름(`ck_…`)을 준다. 값 목록은 Python `StrEnum` 하나에서 가져와 코드와 제약이 어긋나지 않게 한다.
- **updated\_at**: PostgreSQL에는 MySQL의 `ON UPDATE CURRENT_TIMESTAMP`가 없다. 모델에 `onupdate=func.now()`를 두어 SQLAlchemy가 채우게 하고, 행을 바꾸는 UPDATE는 ORM이나 `update()`로만 쓴다. `text()`로 쓴 SQL로 바꾸면 `updated_at`이 그대로다. 보고서 작업 순서(12.4)가 이 값을 쓴다.
- **PostgreSQL을 쓰는 이유**: 세부명세서 9절(개발 요소)이 데이터 저장으로 "PostgreSQL 등 규모에 맞춰 선정"을 권장하고, 팀도 이에 맞춰 PostgreSQL로 정했다(10-20). 드라이버는 BSD 라이선스인 pg8000을 쓴다. 더 널리 쓰는 psycopg 3는 LGPL-3.0이라, 세부명세서 7.1절(납품물에 소스 공개 의무를 만드는 라이선스 금지, 조건이 불명확하면 쓸 수 없음) 검토가 길어질 수 있어서다. Redis는 쓰지 않는다(3절).

**classify\_size 세부**: `app/services/size_class.py`에 `classify_size(weight_kg, *, small_max_kg, medium_max_kg) -> "SMALL" | "MEDIUM" | "LARGE"`로 둔다. 비교는 Decimal로 한다. DB·설정을 읽지 않는 순수 함수라 박규원의 D-14 코드도 이 파일을 그대로 쓴다. `load_breeds(path)`는 견종 이름 목록을 읽어 돌려주고(앞뒤 공백·중복 제거) 체급과는 상관없다. PATCH에 `weight_kg`와 `size_class`가 함께 오면 `size_class`가 이긴다. `size_class: null`로 자동 분류로 돌릴 때는 지금 저장된 `weight_kg`를 쓴다.

견종 목록 형식(예시 세 줄, 실제 목록은 박규원과 함께 채운다):

```yaml
# config/breeds.yaml
- 말티즈
- 웰시코기
- 골든 리트리버
```

## 13. 입력 검증

입력은 아래 표의 순서대로 검사하고, 처음 걸린 것 하나만 오류로 돌려준다. 단, 요청 본문의 필드 형식 오류(길이, 범위, 허용 값)는 Pydantic이 한 번에 모아 `VALIDATION_ERROR`로 돌려주고, 어느 필드인지는 `detail.fields`에 담는다. 오류 코드는 14절에 있다.

### 13.1 영상 업로드

`POST /sessions/{session_id}/shots`에 multipart로 `file` 하나를 받는다.

| 순서 | 검사 | 허용 | 어기면 | 근거 |
| --- | --- | --- | --- | --- |
| 1 | 회차 상태 | `MEASURING` | 409 `SESSION_CLOSED` | 12.4 |
| 2 | 파일 크기 | 최대 100 MB(설정값) | 413 `VIDEO_TOO_LARGE` | 4초 × 16 Mbps ≈ 8 MB라 넉넉하다 |
| 3 | 확장자 | `.mp4`, `.mov`(대소문자 무시) | 400 `VIDEO_FORMAT` | 안드로이드는 mp4, 아이폰은 mov로 찍힌다 |
| 4 | 파일 읽기 | ffprobe가 영상 스트림을 읽을 수 있음 | 400 `VIDEO_UNREADABLE` | 깨진 파일 |
| 5 | 코덱 | `h264`, `hevc` | 400 `VIDEO_CODEC` | PR-F07-01 |
| 6 | 방향 | 가로(회전 정보를 반영한 너비 > 높이) | 400 `VIDEO_PORTRAIT` | 세부명세서 6.5.4 "16:9 가로 촬영" |
| 7 | 길이 | 1\~30초(설정값) | 400 `VIDEO_DURATION` | 촬영 1건은 약 4\~5초 |
| 8 | 최저 사양 | 640×360 이상, 30fps 이상, 4 Mbps 이상 | 받되 경고 `BELOW_MIN_SPEC`, `below_min_spec`=TRUE | 세부명세서 6.5.4 최저 사양 |
| 9 | 화면 비율 | 16:9(±2%) | 받되 경고 `ASPECT_NOT_16_9` | 세부명세서 6.5.4 |

- 파일은 먼저 임시 폴더에 저장해 검사하고, 통과하면 저장소로 옮긴다. 검사에 걸리면 임시 파일을 지우고 DB에는 아무것도 남기지 않는다.
- 너무 큰 요청은 서버 앞 nginx가 먼저 끊고, 앱은 다 받은 파일의 크기를 순서 2에서 확인한다. 받으면서 끊으려면 async 미들웨어가 필요해 11.3과 맞지 않기 때문이다. python-multipart는 시스템 임시 폴더에 먼저 받으므로, 검사 전에 UPLOAD\_TMP\_DIR로 옮긴다. file 필드가 아예 없으면 순서 1보다 먼저 422 VALIDATION\_ERROR다. 서버 앞에 nginx를 두면 `client_max_body_size`도 같은 값으로 맞춘다(허정원).
- 영상 정보는 `ffprobe -v error -show_streams -show_format -of json`으로 읽는다. 휴대폰 영상은 세로로 찍어도 너비·높이는 가로로 저장하고 회전 값(`side_data_list`의 `rotation` 또는 `tags.rotate`)만 남기므로, 회전이 ±90°면 너비와 높이를 바꿔서 판단한다.
- 비트레이트는 영상 스트림의 `bit_rate`를 쓰고, 없으면 파일 크기 × 8 ÷ 길이로 계산한다. fps는 `avg_frame_rate`(예: `60000/1001`)를 나눠서 구한다.
- 경고는 업로드 응답의 `warnings` 배열에 담는다. 경고가 있어도 분석은 그대로 진행한다.

**값 해석**: MB는 1,048,576바이트, kbps는 초당 1,000비트다. 4 Mbps는 4,000 kbps이고 `bitrate_kbps`는 반올림한 정수다. fps는 29.5 이상이면 30fps 기준을 넘은 것으로 본다. 휴대폰 영상은 대개 29.97fps(30000/1001)라, 30으로 자르면 정상 영상이 경고를 받는다. 16:9는 |(너비 ÷ 높이) ÷ (16 ÷ 9) − 1| ≤ 0.02로 판단한다.

## 14. 오류 코드

코드는 네 종류다. API가 바로 돌려주는 응답 오류, 뒤에서 처리하다 실패해 DB에 남는 실패 사유, 분석이 내는 판정·제외 사유, 받아들이되 알려 주는 경고·안내다. 표의 문구는 기본 문구이고, 실제 문구는 `messages/ko.yaml`이 기준이다. 김지윤이 코드를 건드리지 않고 문구를 다듬는다.

- 제외된 통과는 분석 API가 `gait`를 비워 보내므로 `walk_pass.gait_type`은 `OTHER`로 저장한다.
- 사유 코드 목록은 조유진의 판별 결과가 정해지면 그에 맞춰 더하거나 뺀다(10절 Q6).

### 14.5 문구 파일

키는 코드, 값은 화면 문구다. `{max_mb}`처럼 중괄호는 오류의 `detail` 값으로 채운다.

```yaml
# messages/ko.yaml
VIDEO_PORTRAIT: "가로로 촬영한 영상만 올릴 수 있습니다."
VIDEO_TOO_LARGE: "영상 파일이 너무 큽니다. 최대 {max_mb} MB까지 올릴 수 있습니다."
STOPPED: "중간에 멈췄습니다."
```

14절의 모든 코드가 `ko.yaml`에 있는지 테스트로 검사한다. 하나라도 빠지면 테스트가 실패해, 문구 없는 오류가 화면에 나가지 않게 한다.

## 15. API 상세

엔드포인트는 41개이고 주소는 모두 `/api/v1`로 시작한다(27\~41은 v1.12 회원가입·역할·계약). 요청·응답의 필드 이름과 모양은 이 절이 기준이고, 굵게 쓴 객체 이름(**DogOut** 등)을 `schemas/`의 Pydantic 모델 이름으로 그대로 쓴다. 개발 환경(16절 `API_DOCS_ENABLED=true`)에서는 FastAPI가 `/docs`에 시험 화면(Swagger)을 만들어 장준환이 바로 불러 볼 수 있다. 배포에서는 끄고, 기업에 주는 공식 명세는 `docs/openapi.yaml` 하나다.

### 15.1 공통 약속

- **인증**: 로그인, `/health`, `/metrics`, 서명 URL로 여는 파일 두 개(결과 영상, 보고서 PDF), 디바이스 코드 확인·가입(27·28), 비밀번호 재설정 둘(40·41)을 빼고 모두 `Authorization: Bearer <token>`이 필요하다(11.6). `GUEST`(계약이 끝난 `CLIENT`)가 부를 수 있는 것은 1·2뿐이다. `/admin/*`(29\~37) 중 조회는 `ADMIN`·`STAFF`, 쓰기는 `ADMIN`만이다. `/health`와 `/metrics`도 다른 API처럼 `/api/v1` 아래에 둔다(`/api/v1/health`, `/api/v1/metrics`).
- **공통 오류**: 아래 오류는 인증이 필요한 모든 API에서 날 수 있어 엔드포인트마다 다시 적지 않는다. 401 `AUTH_REQUIRED`·`AUTH_EXPIRED`, 403 `ACCOUNT_DISABLED`(로그인 뒤에 계정이 막힘), 403 `CONTRACT_EXPIRED`(기관 계약이 끝난 `CLIENT`, `/auth/me` 제외), 404 `NOT_FOUND`(ID가 없거나 다른 기관의 것), 422 `VALIDATION_ERROR`, 500 `INTERNAL_ERROR`.
- **ID로 찾기**: 주소에 든 ID뿐 아니라 쿼리·본문으로 받은 ID(`base`, `target`, `baseline_session_id`, `target_id`)도 자기 기관 안에서만 찾는다. 반려견에 딸린 회차는 `WHERE id = :id AND dog_id = :dog_id`로 찾는다. 없는 ID와 다른 기관·다른 반려견의 ID는 똑같이 404 `NOT_FOUND`로 답해, 다른 기관에 그 자료가 있는지 알 수 없게 한다. `baseline_session_id`만 예외로 400 `BASELINE_INVALID`다(13.2).
- **ID 형식**: 주소·쿼리·본문의 ID는 `uuid.UUID`로 받는다. 주소(경로)의 ID가 UUID 형식이 아니면 404 NOT\_FOUND(11.5), 쿼리·본문의 ID는 DB까지 가지 않고 422 `VALIDATION_ERROR`다. PostgreSQL은 UUID 컬럼을 UUID 형식이 아닌 문자열과 비교하면 오류를 내므로(그대로 두면 500), 문자열로 받은 ID를 그대로 쿼리에 넣지 않는다.
- **페이지 목록**: 11.5의 `{items, total, page, size}` 모양은 반려견 목록과 측정 이력 두 곳에만 쓴다. 회차의 촬영, 보고서 판본처럼 수가 정해진 묶음은 객체 안의 배열로 준다.
- **사유 객체 Reason**: 사유가 들어가는 자리는 `{"code": "STOPPED", "message": "중간에 멈췄습니다."}` 모양이고(fail\_reason, validity\_reason, exclude\_reason, unmeasurable\_reason, reason, note 모두 같다), 사유가 없으면 `null`이다. `code`는 14절의 값이고 `message`는 `messages/ko.yaml`에서 찾는다. `ANALYZING` 같은 상태 값을 "분석 중"으로 보여 주는 일은 화면이 맡는다.
- **숫자**: DB의 NUMERIC 값은 JSON 숫자로 보낸다. Pydantic v2는 `Decimal`을 문자열로 내보내므로 응답 모델 필드는 `float`로 선언한다. 저장된 값은 반올림하지 않는다. 서버가 계산하는 값(`diff`, `symmetry_index`)과 오차 범위 비교는 float가 아니라 `Decimal`로 한 뒤 내보낸다. float로 빼면 42.0 − 38.2가 3.7999…가 되어 예시·테스트와 어긋난다. `diff`는 소수 넷째 자리, `symmetry_index`는 소수 둘째 자리까지 반올림(`ROUND_HALF_UP`)한다. 표시 자릿수는 화면이 정한다.
- **파일 주소**: `*_url` 필드는 화면이 `src`·`href`에 그대로 넣는 주소다. 저장소가 서버 디스크면 `/api/v1`부터 쓴 상대 주소에 5분짜리 서명이 붙고(11.6), AWS S3면 절대 주소(`http://` 또는 `https://`로 시작)다(11.11). 화면은 상대 주소면 API 주소를 앞에 붙이고, 절대 주소면 그대로 쓴다. 그 밖에는 주소를 고치지 않는다. 함께 오는 `url_expires_at`이 지나면 조회 API를 다시 불러 새 주소를 받는다. 파일이 아직 없으면 `null`이다.
- **쿼리 줄이기**: 목록과 상태 조회는 화면이 자주 부른다. 딸린 행(촬영의 통과 등)은 `selectinload`로 한 번에 읽고, 개수는 `GROUP BY`로 센다. 항목마다 쿼리를 따로 날리지 않는다(N+1 금지).

### 15.3 공통 객체

여러 API가 같은 모양으로 돌려주는 객체다. 값은 예시이고, `"…"`는 UUID다. 필드 이름은 12.2 DDL의 컬럼 이름과 같다. 다른 객체가 통째로 들어가는 자리는 "\<ShotOut>"처럼 객체 이름만 적었다.

### 15.4 인증

**`POST /auth/login`** — 로그인 (BE-01)

```json
// 요청
{"login_id": "kim01", "password": "…"}

// 응답 200
{
  "access_token": "eyJhbGciOi…",
  "token_type": "bearer",
  "expires_at": "2026-10-20T12:10:00Z",
  "staff": "<StaffOut>"
}
```

- 아이디·비밀번호 중 하나라도 틀리면 401 `LOGIN_FAILED` 하나로 답한다(13.4). 순서는 아이디 없음(가짜 해시 비교) → 비밀번호 틀림 → `is_active` FALSE(403 `ACCOUNT_DISABLED`)다. 아이디가 없어도 가짜 해시로 bcrypt 비교를 한 번 해서, 응답 시간으로 아이디가 있는지 알 수 없게 한다.
- 계약이 끝난 `CLIENT`도 로그인되고 `staff.effective_role`이 `GUEST`다. 화면은 그 값을 보고 만료 안내로 보낸다. 로그인은 DB를 직접 읽고 캐시를 갱신한다(11.6).
- `expires_at`은 토큰 만료 시각이다. 화면은 이 시각이나 401 `AUTH_EXPIRED`를 보고 로그인 화면으로 보낸다.

**`GET /auth/me`** — 내 정보. 응답 200 **StaffOut**. DB를 직접 읽고 캐시를 갱신한다. `GUEST`도 된다(계약 검사를 뺀 `CurrentStaffAny`, 11.6).

**`PATCH /auth/me`** — 이름·이메일 수정 (BE-26). 요청 `{"name"?, "email"?}`(보낸 필드만, 규칙은 13.7). 응답 200 **StaffOut**. 바꾼 뒤 자기 스냅샷을 캐시에서 지운다.

**`PATCH /auth/password`** — 비밀번호 변경 (BE-26)

```json
// 요청
{"current_password": "…", "new_password": "…"}

// 응답 200 StaffOut
```

- 현재 비밀번호가 틀리면 400 `PASSWORD_MISMATCH`. 새 비밀번호는 13.7 규칙이다. 바꾼 뒤 자기 스냅샷을 캐시에서 지운다. 이미 받은 토큰은 그대로 유효하다(토큰을 무효화하는 기능은 없다).

**`POST /auth/device-codes/verify`** — 디바이스 코드 확인 (BE-22, 인증 없음)

```json
// 요청
{"code": "7f3k2-qw9pa-x2m8n-h4cde"}

// 응답 200
{"institution": {"id": "…", "name": "크림 재활센터"}, "remaining_accounts": 1}
```

- 코드를 정리해(13.5) 찾고, `revoked_at`이 없고, 기관 계약이 `ACTIVE`여야 200이다. 아니면 404 `DEVICE_CODE_INVALID` 하나다. 응답 본문은 어느 경우든 같다.
- `remaining_accounts` = `max_accounts` − 활성 계정 수(12.5). 0이면 409 `DEVICE_CODE_FULL`.
- DB를 바꾸지 않는다. 몇 번 불러도 같다.

**`POST /auth/signup`** — 회원가입 (BE-22, 인증 없음)

```json
// 요청
{"code": "7F3K2-QW9PA-X2M8N-H4CDE", "login_id": "kim01", "password": "…", "name": "김담당", "email": "kim01@example.com"}

// 응답 201: POST /auth/login의 응답과 같다
```

- 순서: 입력 규칙(422) → 코드 검사(verify와 같은 404·409) → `device_code` 행 잠금 → 활성 계정 수 재확인(409 `DEVICE_CODE_FULL`) → 아이디 중복(409 `LOGIN_ID_TAKEN`) → `staff` 생성(`role` = `CLIENT`, `institution_id` = 코드의 기관, `device_code_id` = 코드, `email`) → 토큰 발급. 가입 즉시 로그인된 상태다(화면이 로그인 화면으로 보내고 싶으면 토큰을 버리면 된다).
- `uq_staff_login` 위반이 동시에 나면(같은 아이디로 동시에 가입) IntegrityError를 409 `LOGIN_ID_TAKEN`으로 바꾼다.
- bcrypt 해시는 DB 작업 전에 끝낸다(트랜잭션을 길게 잡지 않는다. seed.py와 같다). 이메일은 형식만 검사하고 인증 메일은 보내지 않는다.

**`POST /auth/password-reset/request`** — 재설정 링크 보내기 (BE-27, 인증 없음)

```json
// 요청
{"login_id": "kim01"}

// 응답 204 (계정이 있든 없든, 이메일이 있든 없든 같다)
```

- 계정이 있고 활성이고 이메일이 있을 때만 토큰을 만들어 `password_reset_hash`(SHA-256)·`password_reset_expires_at`(now + 30분, 코드 상수 `PASSWORD_RESET_TTL_MIN`)을 저장하고 메일을 보낸다. 링크는 `{FRONTEND_BASE_URL}/reset-password?token={토큰}`이다.
- `SMTP_HOST`가 비어 있으면 계정과 관계없이 503 `MAIL_UNAVAILABLE`. 발송이 실패해도 503이고 저장한 토큰은 지운다.
- 응답 시간으로 계정 유무를 알 수 없게, 계정이 없어도 토큰 생성과 같은 시간이 걸리게 한다(가짜 해시 비교와 같은 생각). 요청 횟수 제한은 없다(15.10).
- `GUEST`(계약 만료)의 계정도 보낸다. 재계약 뒤 바로 쓸 수 있어야 한다. 화면은 "등록된 이메일로 안내를 보냈습니다"를 보여 준다.

**`POST /auth/password-reset/confirm`** — 토큰으로 비밀번호 바꾸기 (BE-27, 인증 없음)

```json
// 요청
{"token": "…", "new_password": "…"}

// 응답 204
```

- 토큰을 SHA-256으로 바꿔 `password_reset_hash`가 같고 `password_reset_expires_at`이 지나지 않은 활성 계정을 찾는다. 없으면 400 `RESET_TOKEN_INVALID`. 새 비밀번호 규칙은 13.4(422).
- 바꾸면 두 칸을 NULL로 하고 그 담당자를 캐시에서 지운다. 화면은 로그인 화면으로 보낸다. 이메일을 잘못 적어 가입한 담당자는 로그인 뒤 `PATCH /auth/me`로 고친다. 로그인도 못 하고 이메일도 틀린 경우는 크림오프 `ADMIN`이 계정을 중지하고 새로 가입하게 한다(상한은 활성 계정만 세므로 자리가 난다).

### 15.5 반려견

**`GET /dogs?q=보리&page=1&size=20`** — 반려견 목록·검색 (BE-03)

- 응답 200: `{"items": [DogOut, …], "total": 45, "page": 1, "size": 20}`
- `q`는 이름에 포함되면 찾는다. 대소문자를 무시하고(`ILIKE`), 검색어 안의 `%`·`_`는 이스케이프한다. SQLAlchemy로는 `Dog.name.icontains(q, autoescape=True)`다.
- 정렬: `last_measured_on` 내림차순(한 번도 안 잰 반려견은 뒤. PostgreSQL은 내림차순에서 NULL을 맨 앞에 두므로 NULLS LAST를 붙인다), 같으면 `created_at` 내림차순.

**`POST /dogs`** — 반려견 등록 (BE-02)

```json
// 요청 (필드 규칙은 13.2)
{
  "name": "보리",
  "breed": "골든 리트리버",
  "weight_kg": 28.4,
  "birth_year": 2019,
  "sex": "FEMALE_SPAYED",
  "rehab_start_date": "2026-10-01",
  "focus_limb": "RH",
  "memo": null
}
```

- 응답 201 **DogOut**.
- `size_class`를 보내지 않으면 `classify_size(weight_kg)`로 정한다(12.5). 보내면 그 값을 쓰고 `size_class_manual`을 TRUE로 한다.
- `baseline_session_id`는 등록 때 받지 않는다. 회차가 아직 없기 때문이다.

**`GET /dogs/{dog_id}`** — 반려견 상세. 응답 200 **DogOut**.

**`PATCH /dogs/{dog_id}`** — 반려견 수정 (BE-02)

```json
// 요청: version은 필수(읽었을 때의 값), 나머지는 바꿀 필드만 보낸다
{"version": 3, "weight_kg": 27.9, "baseline_session_id": "…"}
```

- 응답 200 **DogOut**. 보내지 않은 필드와 `null`을 보낸 필드를 구분해야 하므로 `model_dump(exclude_unset=True)`로 바꿀 값을 꺼낸다.
- `version`(BE-25, 12.5): 저장된 값과 다르면 409 `DOG_MODIFIED`이고 아무것도 바뀌지 않는다. 응답의 `version`은 1 늘어 있다. `version`이 없으면 422.
- `weight_kg`를 바꾸면 `size_class_manual`이 FALSE일 때만 새 체중으로 체급을 다시 정한다. `breed`를 바꿔도 체급은 그대로다(12.5).
- `size_class`에 값을 보내면 `size_class_manual`이 TRUE가 되고, `null`을 보내면 FALSE로 돌아가 자동 분류로 다시 정한다.
- `baseline_session_id`가 이 반려견의 DONE 회차가 아니면 400 `BASELINE_INVALID`다. `null`을 보내면 지정을 풀고 12.5 규칙을 따른다.

### 15.6 회차 측정

**`POST /dogs/{dog_id}/sessions`** — 회차 시작 (BE-04)

```json
// 요청: 두 필드 모두 선택
{"measured_on": "2026-10-20", "weight_kg": 28.1}
```

- 응답 201 **SessionOut**(`status`는 MEASURING).
- `measured_on`을 빼면 오늘(한국 날짜)이다. `weight_kg`를 빼면 `null`로 두고, 보고서는 반려견의 등록 체중을 쓴다.
- `size_class`는 회차 시점 체급이다(12.5 6번): 담당자가 직접 지정한 반려견 체급이 있으면 그 값, 아니면 `weight_kg`(없으면 등록 체중)으로 계산해 저장한다. 이후 반려견 체급이 바뀌어도 회차의 값은 그대로다.
- 이미 MEASURING 회차가 있으면 409 `SESSION_ALREADY_OPEN`이고, `detail.session_id`에 그 회차를 넣는다. 화면은 그 회차로 이동한다.

**`GET /sessions/{session_id}`** — 회차 상태·진행·촬영 목록 (BE-07·09)

S3 화면이 측정하는 내내 2\~3초마다 부르는 API다. 한 번에 화면 전체를 그릴 수 있게 회차·반려견·진행·촬영을 모두 담는다. 응답 200 **SessionDetailOut** = SessionOut의 모든 필드 + 아래.

```json
{
  "dog": {"id": "…", "name": "보리", "breed": "골든 리트리버", "weight_kg": 28.4, "size_class": "LARGE"},
  "progress": {
    "LEFT":  {"valid_passes": 5, "recommended": 8},
    "RIGHT": {"valid_passes": 3, "recommended": 8}
  },
  "notices": [],
  "shots": ["<ShotOut>", "<ShotOut>"]
}
```

- `progress`: 이 회차의 DONE 촬영에서 `is_valid`가 TRUE인 통과를 `camera_side`별로 센다. `recommended`는 설정값 `RECOMMENDED_PASSES`(16절, 기본 8)이고, D-14 결과가 나오면 체급별 값으로 바뀔 수 있다.
- `notices`: 양쪽 모두 권장 수 이상이면 `RECOMMENDED_MET`, 한쪽만 1 이상이고 다른 쪽이 0이면 `ONE_SIDE_ONLY`를 Reason으로 넣는다(14.4).
- `shots`: 이 회차의 촬영 전부를 `seq_no` 내림차순(최신이 위)으로 담는다. 페이지를 나누지 않는다.
- 화면은 `status`가 MEASURING·AGGREGATING인 동안 계속 부르고, DONE이면 S5로, FAILED면 `fail_reason`을 보여 주고 멈춘다.

**`DELETE /sessions/{session_id}`** — 측정 취소 (BE-10)

- 응답 204. S3의 "측정 취소" 버튼이다. 회차와 그 안의 촬영·통과·파일을 12.5 순서로 모두 지운다.
- 회차가 MEASURING이 아니면 409 `SESSION_CLOSED`, SUBMITTED·ANALYZING 촬영이 있으면 409 `SHOT_IN_PROGRESS`다. 분석 중인 촬영을 지우면 워커가 없는 행에 결과를 쓰려고 하기 때문이다.

**`POST /sessions/{session_id}/shots`** — 영상 업로드 (BE-05·06)

- 요청: `multipart/form-data`, 필드 `file` 하나. 파일을 고르든 바로 찍든 같은 API다.
- 13.1 순서로 검사하고, 통과하면 원본을 `{기관ID}/{반려견ID}/{회차ID}/{촬영ID}/original.{mp4|mov}`에 저장한다(7절). 휴대폰의 원래 파일 이름은 어디에도 남기지 않는다.
- `width`·`height`는 회전을 반영한 값(화면에 보이는 방향)으로 저장한다.
- 촬영 행을 UPLOADED로 만들고 바로 응답한다. 분석 요청은 워커가 가져간다(3절, BE-06).

```json
// 응답 201: ShotOut의 모든 필드 + warnings
{
  "id": "…",
  "seq_no": 10,
  "status": "UPLOADED",
  "below_min_spec": true,
  "passes": [],
  "warnings": [
    {"code": "BELOW_MIN_SPEC", "message": "최저 사양(640×360, 30fps, 4 Mbps)보다 낮은 영상입니다. 결과가 부정확할 수 있습니다."}
  ]
}
```

**`POST /sessions/{session_id}/complete`** — 측정 종료 (BE-13)

- 요청 본문 없음. 응답 200 **SessionOut**(`status`는 AGGREGATING, `completed_at` 채움).
- 마지막 촬영의 분석을 기다리지 않고 바로 답한다. 집계와 보고서는 워커가 이어서 한다(12.4).
- 회차가 MEASURING이 아니면 409 `SESSION_CLOSED`, 촬영이 하나도 없으면 409 `SESSION_EMPTY`다.

**`GET /shots/{shot_id}`** — 촬영 상세 (BE-08·11). 응답 200 **ShotDetailOut**. 화면은 `fps`와 통과의 `start_frame`·`end_frame`으로 영상 타임라인에 유효 구간을 표시한다.

**`POST /shots/{shot_id}/retry`** — 다시 분석 (BE-10)

- 요청 본문 없음. 응답 200 **ShotOut**(`status`는 UPLOADED).
- `fail_reason`·`job_id`를 비우고 `attempt_count`를 0, `video_status`를 PENDING으로 돌린다. 남아 있는 통과 행이 있으면 지운다.
- 촬영이 FAILED가 아니면 409 `SHOT_NOT_FAILED`, 회차가 MEASURING이 아니면 409 `SESSION_CLOSED`다.

**`DELETE /shots/{shot_id}`** — 촬영 삭제 (BE-10)

- 응답 204. 파일 → 통과 → 촬영 순서로 지운다. 남은 촬영의 `seq_no`는 다시 매기지 않는다.
- 회차가 MEASURING이 아니면 409 `SESSION_CLOSED`, 촬영이 SUBMITTED·ANALYZING이면 409 `SHOT_IN_PROGRESS`다.

**`GET /shots/{shot_id}/video?exp=…&sig=…`** — 결과 영상 재생 (BE-12)

- 로그인 토큰 없이 서명으로 연다(11.6). 서명은 기관 확인을 거친 조회 API만 만들기 때문에, 서명이 맞으면 기관 확인을 다시 하지 않는다.
- 서명이 틀리거나 `exp`가 지났으면 403 `FILE_LINK_EXPIRED`, `video_status`가 READY가 아니면 404 `NOT_FOUND`다.
- 응답은 `video/mp4` 파일이고, 앞뒤로 넘기기 위한 `Range` 요청(206 응답)을 받는다. Starlette의 `FileResponse`가 Range를 처리하므로 직접 구현하지 않는다. 단, Starlette 0.49.0 이하는 Range 처리에 서비스 거부 취약점(CVE-2025-62727)이 있어, requirements를 고정할 때 0.49.1 이상이 깔리는지 확인한다. `Cache-Control: private, max-age=300`을 붙인다.
- 결과 영상만 내보낸다. 원본 영상을 내보내는 API는 없다(7절).
- 저장소가 S3면 `video_url`이 S3 주소라 이 API는 쓰이지 않고, 불리면 404 `NOT_FOUND`다. Range는 S3가 직접 처리한다(11.11).

**`GET /shots/{shot_id}/angles`** — 프레임별 관절 각도 (BE-14, 권장)

S5의 관절 각도 곡선 그래프에 쓴다(세부명세서 PR-F09-02 "그래프"). DB가 아니라 분석 결과 JSON 파일(`analysis_key`)에서 읽는다.

```json
// 응답 200
{
  "shot_id": "…",
  "fps": 59.94,
  "passes": [
    {
      "pass_no": 1,
      "camera_side": "RIGHT",
      "gait_type": "TROT",
      "start_frame": 42,
      "angles": {
        "shoulder": [112.4, 113.0, null, 114.1],
        "elbow": […], "carpus": […], "hip": […], "stifle": […], "tarsus": […]
      }
    }
  ]
}
```

- 유효 통과의 유효 구간만 담는다. 배열의 i번째 값은 `start_frame + i` 프레임의 각도(°)이고, 관절점을 못 찾은 프레임은 `null`이다. 다리는 `camera_side` 쪽(RIGHT면 RF·RH)이다.
- 촬영이 DONE이 아니면 `passes`는 빈 배열이다.
- 분석 결과에 프레임별 각도가 들어와야 한다. 조유진과 맞출 계약(6절)에 넣었다.

### 15.7 회차 결과·보고서

**`GET /sessions/{session_id}/result`** — 회차 수치와 다리 비교 요약 (BE-14·21)

회차가 DONE이 아니면 409 `SESSION_NOT_DONE`이다. 응답 200 **SessionResultOut** = SessionOut의 모든 필드 + 아래.

```json
{
  "pass_counts": {"measured": 18, "used": 12, "excluded": 6},
  "shot_counts": {"total": 16, "failed": 1, "invalid": 2},
  "exclude_summary": [
    {"code": "RUNNING", "message": "뛰었습니다. 천천히 걷게 해 주세요.", "count": 4},
    {"code": "STOPPED", "message": "중간에 멈췄습니다.", "count": 2}
  ],
  "notices": [],
  "gaits": [
    {
      "gait_type": "TROT",
      "metrics": [
        {"metric_code": "rom_stifle", "limb": "LH", "value": 31.0, "unit": "deg",
         "measurable": true, "unmeasurable_reason": null, "n_passes": 6},
        {"metric_code": "rom_stifle", "limb": "RH", "value": 38.2, "unit": "deg",
         "measurable": true, "unmeasurable_reason": null, "n_passes": 6},
        {"metric_code": "paw_lift", "limb": "LF", "value": null, "unit": "pct_body",
         "measurable": false, "n_passes": 6,
         "unmeasurable_reason": {"code": "LOW_CONFIDENCE", "message": "관절점 인식이 불안정해 계산하지 못했습니다."}}
      ],
      "limb_compare": [
        {"pair": "HIND", "metric_code": "rom_stifle", "unit": "deg",
         "left": 31.0, "right": 38.2, "diff": -7.2, "symmetry_index": 20.81,
         "comparable": true, "reason": null},
        {"pair": "FORE", "metric_code": "paw_lift", "unit": "pct_body",
         "left": null, "right": 12.4, "diff": null, "symmetry_index": null,
         "comparable": false, "reason": {"code": "LOW_CONFIDENCE", "message": "…"}}
      ]
    }
  ]
}
```

- `pass_counts`: 회차의 모든 통과(`measured`), 그중 `is_valid`가 TRUE(`used`)와 FALSE(`excluded`)다. `exclude_summary`는 제외된 통과를 `exclude_reason`별로 센 것이고, 많은 순서다.
- `shot_counts`: 촬영 수, 그중 FAILED 수, `validity`가 INVALID인 수다.
- `gaits`: `session_metric` 행을 보행 유형별로 묶는다(WALK, TROT 순서, 행이 있는 유형만). `metrics`는 12.3 표 순서, 같은 수치 안에서는 LF·RF·LH·RH 순서다. 값은 행 그대로 보낸다(PR-F09-05).
- `limb_compare`(다리 비교 요약, BE-21): 다리별 값이 있는 수치(`walk_speed`·`gait_cycles` 제외)마다 앞다리 쌍(FORE: LF·RF)과 뒷다리 쌍(HIND: LH·RH)을 비교한다. `diff`(왼쪽 − 오른쪽)와 `symmetry_index`는 12.3의 식으로 계산한다(반올림은 15.1).
- 비교할 수 없는 경우: 한쪽 행이 없으면 `reason`은 `NO_DATA`, 한쪽이 측정 불가면 그쪽의 `unmeasurable_reason`(둘 다면 왼쪽)이다. 이때 `comparable`은 false이고, 없는 쪽 값과 `diff`·`symmetry_index`는 `null`이다. 왼쪽 + 오른쪽이 0이면 `comparable`은 true이고 `symmetry_index`만 `null`이다.
- 정렬: `symmetry_index`가 있는 항목을 큰 순서로 먼저, 그다음 `symmetry_index`가 `null`인 비교 가능 항목, 마지막에 비교할 수 없는 항목을 둔다. 같은 값끼리는 12.3 표 순서, 그다음 FORE가 HIND보다 앞이다. 맨 위 항목이 "차이가 가장 큰 다리"다. 백엔드는 아픔·좋아짐 같은 판단 단어를 넣지 않는다(5절).
- `notices`: 15.6과 같은 기준(DONE 촬영의 유효 통과를 보행 유형 구분 없이 `camera_side`별로 셈)으로 `ONE_SIDE_ONLY`를 넣는다(BE-09). `RECOMMENDED_MET`은 넣지 않는다.

**`GET /sessions/{session_id}/reports`** — 판본별 보고서 상태 (BE-15·16)

```json
// 응답 200
{
  "session_id": "…",
  "session_status": "DONE",
  "reports": ["<ReportOut OWNER>", "<ReportOut VET>"]
}
```

- `reports`는 OWNER, VET 순서다. 회차가 DONE이 되기 전에는 빈 배열이다(워커가 회차를 DONE으로 바꾸는 같은 트랜잭션에서 OWNER·VET 두 행을 PENDING으로 만든다, 12.4).
- 화면은 PENDING·GENERATING인 판본이 있는 동안 3초마다 부른다.

**`POST /reports/{report_id}/regenerate`** — 보고서 다시 만들기 (BE-15)

- 요청 본문 없음. 응답 200 **ReportOut**(`status`는 PENDING, `fail_reason`은 `null`). GENERATING이면 409 `REPORT_IN_PROGRESS`다.
- 같은 행을 덮어쓴다(12.2). 보고서 키는 보고서 ID로 정해져 바뀌지 않으므로, 워커는 같은 키에 새 PDF를 덮어쓰고 예전 파일을 따로 지우지 않는다(12.4). 실패(FAILED)하면 예전 PDF가 남지만, 파일 API는 DONE일 때만 연다.

**`GET /reports/{report_id}/file?exp=…&sig=…&download=true`** — PDF 미리보기·내려받기 (BE-16)

- 서명 확인은 결과 영상과 같다. 보고서 `status`가 DONE이 아니면 404 `NOT_FOUND`다. 다시 만드는 중이거나 실패한 판본의 예전 PDF는 내보내지 않는다.
- `Content-Type: application/pdf`. `download=true`면 `Content-Disposition: attachment`, 없으면 `inline`이다.
- 내려받는 파일 이름은 `{반려견 이름}_{측정일}_{보호자용|수의사용}.pdf`이다. 한글이라 `filename*=UTF-8''<퍼센트 인코딩>` 형식으로 넣는다. 저장소 경로에는 여전히 이름을 쓰지 않는다(7절).
- 저장소가 S3면 `file_url`·`download_url`이 S3 주소다. `download_url`은 presigned URL에 같은 `Content-Disposition`(첨부, 같은 파일 이름)을 넣어 만든다(11.11).

### 15.8 이력·비교·추이

**`GET /dogs/{dog_id}/sessions?page=1&size=20`** — 측정 이력 (BE-17)

- 응답 200: `{"items": [SessionHistoryItem, …], "total": 5, "page": 1, "size": 20}`. 정렬은 `measured_on` 내림차순, 같으면 `created_at` 내림차순이다.

```json
// SessionHistoryItem
{
  "id": "…",
  "measured_on": "2026-10-20",
  "weight_kg": 28.1,
  "status": "DONE",
  "is_baseline": true,
  "valid_passes": {"LEFT": 8, "RIGHT": 8},
  "model_version": "v1",
  "reports": {"OWNER": "DONE", "VET": "FAILED"}
}
```

- `is_baseline`은 12.5 규칙으로 정한 기준 회차인지다. `reports`는 판본별 `status`이고 행이 없으면 `null`이다.

**`GET /dogs/{dog_id}/compare?target=…&base=BASELINE&gait_type=TROT`** — 회차 비교 (BE-18)

| 쿼리 | 필수 | 뜻 |
| --- | --- | --- |
| `target` | 선택 | 비교할 회차 ID. 기본은 가장 최근 DONE 회차 |
| `base` | 선택 | `BASELINE`(기본, 기준 회차), `PREVIOUS`(`target` 바로 앞 DONE 회차), 또는 회차 ID |
| `gait_type` | 선택 | 주면 그 보행 유형만 낸다 |

```json
// 응답 200
{
  "dog_id": "…",
  "base":   {"session_id": "…", "measured_on": "2026-10-01", "model_version": "v1", "kind": "BASELINE"},
  "target": {"session_id": "…", "measured_on": "2026-10-20", "model_version": "v1"},
  "model_changed": false,
  "items": [
    {"metric_code": "rom_stifle", "limb": "RH", "gait_type": "TROT", "unit": "deg",
     "base_value": 38.2, "target_value": 42.0, "diff": 3.8,
     "judgement": "UNKNOWN",
     "note": {"code": "RANGE_NOT_SET", "message": "변화 판단 기준이 아직 정해지지 않았습니다."}}
  ]
}
```

- `items`는 어느 한쪽 회차에라도 있는 (`gait_type`, `limb`, `metric_code`) 조합을 모두 낸다(합집합). 정렬은 보행 유형, 다리(반려견의 `focus_limb` 먼저, 나머지는 LF·RF·LH·RH·NONE), 12.3 표 순서다.
- `diff` = `target_value` − `base_value`. `kind`는 `BASELINE`·`PREVIOUS`·`SESSION`(회차 ID로 지정) 중 하나다.
- 가장 최근, 바로 앞, 기준 회차는 모두 12.5의 회차 순서를 따른다.
- `target`·`base`로 받은 회차 ID는 이 반려견 안에서만 찾는다. 없거나 다른 반려견·다른 기관의 회차면 404 `NOT_FOUND`다(15.1).

`judgement`는 아래 순서로 처음 맞는 줄을 따른다(5절 비교 규칙). 로직은 `services/compare.py` 한 곳에 둔다.

| 순서 | 조건 | `judgement` | `note` | `diff` |
| --- | --- | --- | --- | --- |
| 1 | 한쪽 회차에 그 행이 없거나 측정 불가 | `NOT_COMPARABLE` | 행이 없는 쪽이 있으면 `NO_DATA`, 아니면 base 쪽, 그다음 target 쪽의 `unmeasurable_reason` | `null` |
| 2 | 두 회차의 `model_version`이 다름 | `UNKNOWN` | `MODEL_CHANGED` | 값 |
| 3 | `config/tolerance.yaml`에 그 수치의 오차 범위가 없음 | `UNKNOWN` | `RANGE_NOT_SET` | 값 |
| 4 | \|`diff`\| ≤ 오차 범위 | `WITHIN_RANGE` | `null` | 값 |
| 5 | `diff` > 오차 범위 / `diff` < −오차 범위 | `INCREASE` / `DECREASE` | `null` | 값 |

오차 범위 파일은 수치 코드별로 원 단위 값을 넣는다. 기업 값을 받기 전(10절 Q4)에는 비워 두어 모두 `UNKNOWN`이 나오게 한다.

```yaml
# config/tolerance.yaml (예시. 값은 10절 Q4 답을 받으면 채운다)
rom_stifle: 3.0      # deg
stride_length: 2.0   # pct_body
```

비교할 수 없는 요청은 400 `COMPARE_INVALID`이고, `detail.reason`에 아래 중 하나를 넣는다. 화면은 이 값으로 "비교할 회차가 없습니다" 같은 빈 화면을 고른다.

- `NO_DONE_SESSION`: DONE 회차가 하나도 없다.
- `SAME_SESSION`: `base`와 `target`이 같은 회차다(예: 회차가 하나뿐이라 기준 회차가 곧 최근 회차).
- `NO_PREVIOUS`: `base=PREVIOUS`인데 `target` 앞에 DONE 회차가 없다.
- `NOT_DONE`: 지정한 회차가 DONE이 아니다.

**`GET /dogs/{dog_id}/trends?metric_code=rom_stifle&gait_type=TROT`** — 수치 추이 (BE-18)

| 쿼리 | 필수 | 뜻 |
| --- | --- | --- |
| `metric_code` | 필수 | 12.3 표의 코드 |
| `gait_type` | 필수 | 같은 보행 유형끼리만 잇는다(PR-F08-14) |
| `limb` | 선택 | 주면 그 다리만 낸다 |
| `from`, `to` | 선택 | `measured_on` 기간(날짜 포함) |

```json
// 응답 200
{
  "dog_id": "…",
  "metric_code": "rom_stifle",
  "unit": "deg",
  "gait_type": "TROT",
  "series": [
    {"limb": "RH", "points": [
      {"session_id": "…", "measured_on": "2026-10-01", "value": 38.2, "measurable": true,
       "unmeasurable_reason": null, "model_version": "v1"},
      {"session_id": "…", "measured_on": "2026-10-20", "value": 42.0, "measurable": true,
       "unmeasurable_reason": null, "model_version": "v1"}
    ]},
    {"limb": "LH", "points": ["…"]}
  ],
  "lr_diff": [
```

- DONE 회차만, `measured_on` 오름차순이다. 그 회차에 행이 없으면 점을 넣지 않고, 측정 불가면 `value`가 `null`인 점을 넣는다.
- `series`는 `focus_limb`를 먼저 두고 나머지는 LF·RF·LH·RH 순서다.

- 모델 버전이 바뀐 점은 화면이 `model_version`을 보고 표시한다(5절).

### 15.9 운영

**`POST /admin/purge`** — 자료 파기 (BE-19, 관리자만)

```json
// 요청
{"scope": "DOG", "target_id": "…", "dry_run": true}

// 응답 200
{"scope": "DOG", "target_id": "…", "dry_run": true,
 "rows": 214, "files": 49, "bytes": 391000000, "purge_log_id": null}
```

- `scope`는 `DOG`(`target_id` = 반려견 ID) 또는 `INSTITUTION`(자기 기관 전체, `target_id` 생략)이다. 여러 기관을 한꺼번에 지우는 `ALL`은 API로 열지 않고 서버에서 `python -m scripts.purge --all`로만 한다.
- `dry_run`의 기본값은 true다. 지울 행·파일·용량만 세고 아무것도 지우지 않는다. 실제로 지우려면 false를 분명히 보낸다.
- 실제로 지우면 `purge_log`에 1행을 남기고 그 ID를 `purge_log_id`로 돌려준다. 파기 확인서(D-13)의 근거다.
- `INSTITUTION`은 반려견과 그 아래 자료를 모두 지우고, 기관과 담당자 계정은 남긴다.
- 대상에 SUBMITTED·ANALYZING 촬영이 있으면 409 `SHOT_IN_PROGRESS`다. `role`이 ADMIN이 아니면 403 `FORBIDDEN`이다.

**크림오프 관리자 API** (BE-24, 11.6 역할 검사: 조회는 `ADMIN`·`STAFF`, 쓰기는 `ADMIN`. 기관·코드·계정 메타데이터까지만 다루고 고객 자료는 열지 않는다. 10절 Q31)

- **`GET /admin/institutions`** — 응답 200 `{"items": [InstitutionAdminOut, …]}`. 페이지 없이 전체다(기관 수가 작다). `name` 오름차순.
- **`POST /admin/institutions`** — 요청 `{"code": null, "name": "크림 재활센터", "contract_ends_at": "2027-10-30"}`(규칙은 13.6). 응답 201 **InstitutionAdminOut**.
- **`PATCH /admin/institutions/{id}`** — 요청 `{"name"?, "contract_ends_at"?}`(보낸 필드만, `null`은 기한 없음). 응답 200 **InstitutionAdminOut**. 바꾼 뒤 그 기관 담당자를 캐시에서 지운다.
- **`GET /admin/institutions/{id}/device-codes`** — 응답 200 `{"items": [DeviceCodeOut, …]}`. 회수된 코드도 포함한다(`revoked_at`으로 구분).
- **`POST /admin/institutions/{id}/device-codes`** — 요청 `{"max_accounts"?: 3, "note"?: "2호기"}`. 응답 201 **DeviceCodeOut**.
- **`PATCH /admin/device-codes/{id}`** — 요청 `{"max_accounts"?, "note"?}`. 상한을 활성 계정 수보다 낮게 내릴 수 있다(그 뒤 가입만 막힌다). 응답 200 **DeviceCodeOut**.
- **`POST /admin/device-codes/{id}/revoke`** — 본문 없음. `revoked_at`을 now()로. 이미 회수됐으면 그대로 200. 기존 계정은 그대로 쓴다(막으려면 계정 중지). 응답 200 **DeviceCodeOut**.
- **`GET /admin/institutions/{id}/staff`** — 응답 200 `{"items": [{id, login_id, name, email, role, is_active, device_code_id, created_at}, …]}`.
- **`PATCH /admin/staff/{id}`** — 요청 `{"is_active": false}`. 응답 200: 위 목록의 항목 하나. 자기 자신에게 false를 보내면 409 `SELF_DISABLE`. 바꾼 뒤 그 담당자를 캐시에서 지운다. 역할을 바꾸거나 비밀번호를 건드리는 필드는 없다.
- 없는 ID는 404 `NOT_FOUND`다. 관리자 API는 기관 필터가 없다(크림오프가 모든 기관을 본다).

**`GET /health`** — 서버 상태 (BE-20)

- 인증 없음. Docker 상태 검사가 부른다.
- 응답 200 `{"status": "ok", "db": "ok", "storage": "ok", "version": "1.0.0"}`. DB 접속(`SELECT 1`)이나 저장소 쓰기 검사(11.11)가 실패하면 503이고, 실패한 항목은 `"error"`다.

**`GET /metrics`** — 요청 수·처리 시간 (BE-20, 선택)

- Prometheus 텍스트 형식. 인증이 없으므로 밖에서 열리지 않게 내부망에서만 받는다. 방식은 허정원과 정한다(11.8).

### 15.10 이번 API에 없는 것

5절의 선택 기능(재분석, 영상 나란히 보기, 경과 요약)과 유저플로우의 후순위 화면(S9 기관 선택, S10 운영 설정)은 API가 없다. 모델 전환과 판정 기준은 설정 파일로 대신한다(PR-F07-04, PR-F03-07). 만들기로 하면 이 절에 먼저 추가하고 문서 버전을 올린 뒤 구현한다.

회원가입·역할·계약(v1.12)에서 일부러 뺀 것: 가입 이메일 인증(디바이스 코드가 이미 고객 증명이다), 계약 만료 알림 메일, 메일 재발송 횟수 제한(토큰 30분 만료로 대신), 관리자 계정을 만드는 API(`seed.py`), 관리자가 비밀번호를 재설정하는 경로, 역할 변경 API, 병원 측 관리자 역할, 크림오프 쪽의 고객 자료 열람(10절 Q31), 휴대폰 인증, 코드 재발급(회수 + 새 발급으로 대신), 자동 역할 변경·스케줄러, 등급(`plan`), refresh token, 토큰 무효화(로그아웃은 화면이 토큰을 버리는 것), 요청 횟수 제한(코드 길이 100비트로 대신).

- **필수 값**: 비어 있거나 `JWT_SECRET`·`FILE_URL_SECRET`이 32자보다 짧으면 서버와 워커가 켜지지 않고 어느 값이 문제인지 알려 주며 멈춘다. `STORAGE_BACKEND`가 `s3`인데 `S3_BUCKET`이 비어 있어도 같다. 무작위 값은 `python -c "import secrets; print(secrets.token_urlsafe(48))"`로 만든다.
- **비밀값**: `DATABASE_URL`, `JWT_SECRET`, `FILE_URL_SECRET`, `ANALYSIS_API_KEY`, `S3_SECRET_ACCESS_KEY`, `SMTP_PASSWORD`는 `SecretStr`로 선언해 로그·오류 화면에 찍히지 않게 한다. `.env`는 git에 올리지 않고, `.env.example`에 이 표의 이름과 기본값만 둔다.
- **CORS**: 화면(React 개발 서버)과 API의 주소가 다르면 브라우저가 요청을 막는다. FastAPI `CORSMiddleware`에 `CORS_ORIGINS`만 허용하고, `*`는 쓰지 않는다. 기본값 5173은 Vite 개발 서버 포트이며, 장준환의 개발 서버 주소에 맞춘다. 서명 URL과 S3 주소로 여는 영상·PDF는 태그가 직접 부르므로 CORS와 상관없다.
- **토큰 만료**: 토큰을 새로 받는 기능(refresh token)은 두지 않는다. 12시간이면 하루 근무가 끝날 때까지 끊기지 않고, 지나면 다시 로그인한다.
- **상수로 두는 값**: 세부명세서가 정한 최저 사양(640×360, 30fps, 4 Mbps), 허용 코덱, 16:9 허용 범위(±2%), 재설정 토큰 유효 시간(30분)은 바뀔 일이 없어 환경 변수가 아니라 코드 상수로 둔다.
- **Docker**: PostgreSQL 컨테이너(`postgres:17-alpine`, 팀 서버 compose와 같은 이미지)의 변수(`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`)와 볼륨 경로는 `docker-compose.yml`에서 허정원과 맞춘다. 17까지는 볼륨을 `/var/lib/postgresql/data`에 붙이고, 18로 올릴 때는 `/var/lib/postgresql`로 바꾼다(18부터 데이터 폴더 구조가 달라져 예전 경로에 붙이면 컨테이너가 켜지지 않는다). 메이저 버전을 바꾸면 기존 볼륨은 읽지 못하므로 `docker compose down -v`로 지우고 다시 띄운다. db 서비스의 healthcheck는 `pg_isready`로 하고, api·worker는 db가 healthy가 된 뒤 켠다. api 컨테이너는 시작할 때 alembic upgrade head를 먼저 실행하고, `/docker-entrypoint-initdb.d/`의 초기화 스크립트로 테스트용 DB(creamoff\_test)도 만든다.
- **워커 CPU 상한**: `docker-compose.yml`의 worker 서비스에 `cpus`를 걸어 API가 쓸 코어를 남긴다. 값은 팀 서버 사양을 보고 정한다(10절 Q22). 예를 들어 4코어면 `cpus: "3"`이다.

개발 환경에서 최소로 채울 `.env`:

```text
DATABASE_URL=postgresql+pg8000://creamoff:creamoff@localhost:5432/creamoff
TEST_DATABASE_URL=postgresql+pg8000://creamoff:creamoff@localhost:5432/creamoff_test
JWT_SECRET=<무작위 값>
FILE_URL_SECRET=<다른 무작위 값>
STORAGE_ROOT=./data/files
UPLOAD_TMP_DIR=./data/tmp
ANALYSIS_API_MODE=mock
```

**기업 환경에 설치할 때**: 실행 가이드(D-09)의 팀 서비스 부분은 아래 순서로 쓴다. 백엔드가 초안을 쓰고 허정원이 가이드에 넣는다.

1. 운영체제 패키지: ffmpeg(ffprobe 포함), WeasyPrint가 쓰는 Pango 등 시스템 라이브러리, 한글 OFL 글꼴. requirements.txt 밖의 전제라 가이드에 적는다(PR-C-07).
2. Python 3.11 `.venv`를 만들고 `pip install -r requirements.txt`(버전 고정)로 설치한다. Docker 없이도 설치되어야 한다(PR-C-07).
3. `STORAGE_ROOT`·`UPLOAD_TMP_DIR` 폴더를 같은 볼륨에 만들고, API와 워커를 띄우는 계정에 쓰기 권한을 준다.
4. PostgreSQL 17을 준비하고 `.env`를 채운다. 꼭 채울 값은 `DATABASE_URL`, `JWT_SECRET`, `FILE_URL_SECRET`, `CORS_ORIGINS`(기업 화면 주소), `ANALYSIS_API_MODE`·`ANALYSIS_API_BASE_URL`·`ANALYSIS_API_KEY`다. 저장소는 기업이 고른 쪽으로 `STORAGE_BACKEND`와 그에 딸린 값을 넣는다(7절, 10절 Q19).
5. `alembic upgrade head`로 테이블을 만들고, `python -m scripts.seed`로 기관·관리자 계정을 만든다.
6. API(`uvicorn app.main:app --no-access-log`)와 워커(`python -m app.worker.main`)를 따로 띄운다. 워커는 하나만 띄운다(12.4). Docker 없이 띄우면 `cpus` 상한이 없으므로, systemd의 `CPUQuota`로 워커의 CPU를 묶거나 `WORKER_RENDER_CONCURRENCY`를 코어 수보다 작게 둔다.
7. `/api/v1/health`가 200인지, 17.7 시연 시나리오가 Mock 모드에서 도는지 확인한다.

## 17. 완료 조건

기능마다 "이것이 되면 끝"을 확인할 수 있는 문장으로 적었다. 한 줄이 테스트 하나가 되도록 썼고, 조영운의 단위 테스트와 김지윤의 API 시험표가 이 목록을 기준으로 한다. AI에 작업을 맡길 때도 해당 줄을 함께 넣는다(18절).

### 17.1 공통

- [ ] 토큰 없이 부르면 401 `AUTH_REQUIRED`, 만료된 토큰이면 401 `AUTH_EXPIRED`다.
- [ ] 다른 기관 담당자가 주소·쿼리·본문에 이 기관의 ID를 넣으면 404 `NOT_FOUND`이고, 없는 ID를 넣었을 때와 응답 본문이 같다.
- [ ] 모든 오류 응답이 11.5 모양이고, `code`는 14절에 있으며 `message`는 `ko.yaml` 문구다.

- [ ] 로그에 반려견 이름, 담당자 이름, 비밀번호, 토큰, 파일 경로, 디바이스 코드, 재설정 토큰, 이메일 주소가 남지 않는다(11.8).

### 18.2 AI에 넣는 법

넣는 것은 네 가지다. 이 문서를 Markdown으로 내려받아 절 단위로 잘라 붙인다.

1. **11절 전체**: 모든 작업에 항상 넣는다.
2. **18.1 표의 "AI에 넣을 절"**: 12.2 DDL은 그 작업에 필요한 테이블만 잘라도 된다.
3. **17절의 해당 줄**: AI가 테스트로 옮길 기준이다.
4. **이미 만든 관련 파일**: `models/`, `schemas/`, `core/errors.py`처럼 새 코드가 기대는 파일이다.

18.1 표에 1부 절(3·5·6·7·8절)이 있으면 그 절도 넣고, 나머지 1부는 넣지 않는다. 2부와 다르면 2부가 기준이고, 글이 길어질수록 AI가 지시를 놓친다. 아래 틀에 채워 넣는다.

```text
너는 이 프로젝트의 백엔드 개발자다. [규약]과 [명세]를 지켜 [작업]을 구현해라.

[작업]
작업 단위 5: 회차 시작·조회·취소, 업로드 검사·저장, StorageService

[규약]
(11절 전체를 붙인다)

[명세]
(7절, 13.1, 13.3, 15.3, 15.6, 12.2의 measure_session·shot·walk_pass를 붙인다)

[완료 조건]
(17.3의 BE-04·05 줄을 붙인다)

[이미 있는 코드]
(app/models/measure_session.py, app/models/shot.py, app/core/errors.py 등을 붙인다)

[출력 규칙]
- 파일마다 경로를 먼저 쓰고 전체 내용을 준다. 일부만 주거나 "생략"하지 않는다.
- 완료 조건 줄마다 pytest 테스트를 하나 이상 만든다.
- 명세에 없는 엔드포인트·필드·테이블·환경 변수·오류 코드를 만들지 않는다.
- 명세로 정할 수 없는 부분은 추측하지 말고 코드에 # TODO(질문: …)를 남기고, 답 끝에 그 목록을 따로 적는다.
```

터미널에서 저장소를 직접 읽는 도구(Claude Code, Codex 등)를 쓰면 매번 붙이지 않아도 된다. 이 문서의 Markdown을 저장소의 `docs/backend-spec.md`에 두고, 저장소 맨 위 `CLAUDE.md`(Codex는 `AGENTS.md`)에 "코드를 쓰기 전에 docs/backend-spec.md의 11절을 읽고 지킨다"와 위 출력 규칙을 적는다. 작업을 맡길 때는 "작업 단위 5를 해라. 18.1 표의 절과 17.3의 BE-04·05를 따른다"처럼 절 번호를 짚는다.

### 18.3 받은 코드 확인

- [ ] pytest를 돌려 완료 조건 테스트가 모두 통과한다. 통과시키려고 AI가 테스트의 기대값을 명세와 다르게 바꾼 곳이 없다.
- [ ] 명세에 없는 이름이 생기지 않았다: 엔드포인트, JSON 필드, 테이블·컬럼, 환경 변수, 오류 코드.
- [ ] AI가 자주 하는 실수가 없다: `async def`, `session.query()`, SQLite 테스트, 코드에 직접 쓴 화면 문구, float로 한 차이 계산, 기관 필터가 빠진 조회, StorageService를 거치지 않은 파일 읽기·쓰기.
- [ ] TODO 목록을 읽고, 문서로 답이 안 나오는 것은 10절에 질문으로 올린다.

### 18.4 명세를 바꿔야 할 때

코드만 고치지 않는다. 문서를 먼저 고치고, 문서 정보 표에 버전과 바뀐 내용을 한 줄 남긴 뒤, 저장소의 `docs/backend-spec.md`도 바꾼다. 그래야 다음 사람이 AI에 넣는 명세와 이미 있는 코드가 어긋나지 않는다. 화면·시험에 영향을 주는 변경(15·17절)은 장준환·김지윤에게 바로 알린다.
